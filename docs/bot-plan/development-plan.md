# План разработки и проверок

Торговая точка истины — локальный `strategy/fvg-bot-rules.json`, торговая редакция
`agreed-v4`, формат v2. [Требования](requirements.md) задают продукт, [архитектура](architecture.md)
— устройство. Этот документ содержит порядок работ, критерии приёмки и датированные
результаты. Старые проверки не подтверждают более поздние изменения JSON или кода.

## Текущее состояние

### Исследование swing, 17.11.2026

По отдельному запросу пользователя провести исторические сравнения только swing
на текущем коде ветки v1.0.0. Рабочие правила автоматически не менять.
Использовать `swing-history` в Docker и существующие подготовленные M1 MT5
EURUSD/GBPUSD/USDJPY; сетка результатов — время Нью-Йорка + 7 часов,
цены исходных данных — миллионные доли, вход swing — десятичная цена.
Пропуски не заполнять, исходные файлы не менять. Это модель по минутным экстремумам,
не подтверждение исполнения по живому индексу Upscale; стоп при одновременном
достижении стопа и тейка имеет приоритет. `cost` учитывается существующим движком.

До просмотра результатов зафиксировать ограниченный набор однофакторных вариантов
RR, цели, срока плана, защитного буфера/окна стопа, подтверждения, времени входа
и включения боковика. Начало торговли — 01.09.2020 после прогрева с января.
Выбор вариантов — только по 2020–2023; 2024 используется для хронологической
проверки устойчивости; 2025–12.11.2026 — последующая проверка без новых настроек.
История уже использовалась ранее: эти периоды не считать нетронутым holdout.
Границы статистики обозначать в сетке swing; сделки, переходящие границы,
раскрывать, не приписывая будущие выходы прошлому периоду.

Оценивать число сделок, суммарный/средний R, profit factor, просадку закрытого R,
результаты по годам, парам и типам планов, концентрацию прибыли, открытые сделки.
Для базового и выбранных устойчивых вариантов выполнить дополнительные прогоны
с повышенными издержками; проверить соседние значения и месячную устойчивость.
Не выбирать результат по одной максимальной прибыли. Остановить поиск после
проверки зафиксированного набора и стрессов; отсутствие устойчивого улучшения
тоже является выводом. Хеши кода/конфигураций/источников, команды, время выполнения
и таблицы сохранить в новом каталоге `reports/backtests/swing-research-20261117`.

Результат исследования 17.11.2026: по train-only до открытия 2024/later были
заморожены baseline, `stop_lookback_h4_bars=15` и `range.enabled=false`; прочие
14 preregistered вариантов сохранены, новые комбинации после просмотра later не
добавлялись. В train их закрытый net R / максимальная закрытая просадка / число
сделок: baseline 52.40 / 10.60 / 241, lookback15 54.98 / 10.13 / 239,
range_off 32.76 / 6.20 / 110. В 2024 это соответственно +2.38, +3.51 и
−12.56R; в 2025–12.11.2026 +34.95, +40.92 и +34.14R. Закрытый R относится к
периоду выхода `[start,end)`; сделки через границу не переигрываются, carry-in
показывается отдельно. Закрытая кривая и её DD для каждого периода начинают с
нулевой equity, тогда как отдельная полная MTM-кривая непрерывна. История ранее
использовалась, поэтому ни validation, ни later не являются
независимым holdout.

Фактические x2/x3 cost reruns выполнены для всех трёх финалистов и всех трёх
пар (18/18 exit 0; вместе с первоначальными 51 — 69 успешных запусков). Результат
lookback15 выше baseline в train и later при обеих надбавках, но 2024 при x3
отрицателен; 3-месячный paired moving-block bootstrap для разницы lookback15 минус
baseline даёт validation +1.13R, 95% CI [−4.66, +8.02], later +5.97R,
[−0.005, +11.91]. Это условная оценка для выбранных параметров и повторно
использованной истории, не p-value и не поправка на перебор. Поэтому lookback15
остаётся кандидатом для независимой последующей проверки, а не рекомендацией для
production; range_off не поддержан периодом 2024. Портфельная оценка по общим
наблюдаемым MT5 M1 close (без заполнения пропусков) даёт continuous mark-to-market
DD 23.20R / 23.67R / 26.24R для baseline / lookback15 / range_off: lookback15
выше baseline на 0.47R. Отдельный overlay ещё одного гипотетического pip даёт DD
24.68R / 24.61R / 28.55R; это дополнительный стресс, а не фактический x2/x3
replay. Максимум на минутных отметках — 6 одновременно открытых позиций/6
начальных R; оценка не моделирует маржу, денежные размеры или внутри-минутный риск.

Метрики, периоды, carry-in/open positions, leave-one-year/pair, MTM, source
coverage, bootstrap и cost outputs находятся в `period-analysis.json` и
`period-metrics.csv`; shortlist — `selection.json`, окружение и хеш БД —
`run-environment.json`. Исполнялись актуальный release Docker-бинарник
`6b5caaab…ffa16195` (rustc/cargo 1.85.1) без сети и analysis helper в
`/tmp/forex-research-20261116-venv`; рабочие правила и реализация не менялись.

При последующей проверке analysis helper два synthetic RED-теста воспроизвели
ошибки: годовые stats включали сделки за пределами частичного периода (4 вместо
2 в fixture), а integer rounding менял 1.23456789 на 1.234568 при конвертации

Это контроль точности расчёта, без вывода об экономической значимости.

### Ограниченная оптимизация swing, протокол до прогонов, 17.11.2026

Пользователь отдельно разрешил исследовательский поиск параметров swing и
последующий просмотр рабочего JSON только при выполнении заранее определённого
promotion gate. Все доступные даты истории уже использовались в прежних
исследованиях; поэтому даже walk-forward здесь не будет нетронутой внешней
проверкой и не доказывает прибыльность в будущем. До получения результатов
фиксируется одна поисковая стадия и не более одной диагностической стадии;
неудача любого обязательного gate завершает поиск без изменения рабочего JSON.
Подбор остаётся офлайн-исследованием и не расширяет функциональные требования
приложения.

Первая стадия использует 128 уникальных конфигураций Optuna 4.6.0
QMCSampler/Sobol с фиксированным seed и исходные три пары; первый trial —
seeded RandomSampler для установления пространства, следующие 127 — Sobol,
поэтому это QMC-пул, не чистый 128-точечный Sobol net. Плюс baseline — всего
387 прогонов.
Параметры общие для трёх пар: `rr_fixed`, `take_profit`/`rr_target_cap`,
`plan_days`, `stop_lookback_h4_bars`, `stop_buffer_atr`, режим подтверждения,
профиль часов входа и `range.enabled`. Сетка значений, seed, exact search-space,
canonicalization, команды и sample cap до запусков сохраняются в
`reports/backtests/swing-optimization-20261117/protocol.json`. Пространство
дискретно; стоимость сделки и `start` не оптимизируются. Полный replay каждого
набора строится один раз на тех же MT5 M1 данных; выбор единственного кандидата
использует только выходы в train `[2020-09-01, 2024-01-01)`, по общей net R
(издержки движка уже применены), с заранее указанными tie-break. После этого
добавлять параметры или итерации нельзя.

Единственная диагностическая стадия заранее ограничена: (a) новая пара
сравнительных replay на одном и том же свежем старте 2024-01-01 и конце
2026-11-12 для зафиксированного кандидата и baseline; `start` задаётся Unix
секундами наивной source-grid строки, а не UTC моментом, предыдущие позиции
отсутствуют; (b) cost ×2/×3 для этих двух конфигураций; (c) детерминированные
одношаговые соседи победителя по той же сетке; (d) один заранее ограниченный
annual walk-forward 2022–2026, выбирающий каждый год только из прежней истории
фиксированного пула и запускающий выбранное правило и baseline fresh с января
тестового года. Соседи строятся в порядке из `protocol.json`, не заменяют
победителя; для локальной устойчивости положительный net-R uplift должны иметь
не менее половины соседей, медианный uplift также должен быть положительным.
WFO выбирает конфигурацию только если prior net R не ниже baseline, closed DD и
exposure не выше baseline; иначе на тестовый fold берётся baseline. Позиции у конца периода показываются отдельно по последней
общей наблюдаемой котировке до cutoff. Годовой fold — диагностическая
counterfactual-проверка, а не independent holdout.

Критерий значительного результата задан до подбора. Так как baseline net R
положителен, frozen candidate должен превысить baseline не менее чем на 25%
(и абсолютную разницу считать в R) как за всю историю, так и на свежем
сопоставимом интервале 2024–12.11.2026. На обоих интервалах его full
mark-to-market DD с фактическими издержками не должен превышать baseline; не
должны расти пиковые открытые позиции и начальный риск, ни суммарно, ни по паре.
Дополнительно обязательны пары/годы, actual cost ×2/×3, соседние значения и
selection-aware conditional block-Monte-Carlo по всему QMC pool; не менее чем
в 3 из 5 WFO folds net R должен превысить fresh baseline, все folds показаны с
train-only выбором. Объективная спецификация,
состав и жёсткие gate записаны в `protocol.json` до результатов. Conditional
max-stat показывает только чувствительность к перебору в этом фиксированном
пуле и блочной модели; он не корректирует предыдущие просмотры этой истории,
не является независимой проверкой и не служит p-value рыночной доходности.
Sharpe/Deflated Sharpe не применяется к аддитивным единицам R как к денежным
доходностям.

Первичные методические ссылки: [Optuna 4.6.0 QMCSampler](https://optuna.readthedocs.io/en/v4.6.0/reference/samplers/generated/optuna.samplers.QMCSampler.html),
[walk-forward optimization](https://www.quantconnect.com/docs/v2/writing-algorithms/optimization/walk-forward-optimization),
[Deflated Sharpe paper](https://davidhbailey.com/dhbpapers/deflated-sharpe.pdf).

Результат оптимизации, 17.11.2026: 128 unique QMC конфигураций и baseline
дали 387/387 успешных stage-one прогонов; единственная диагностическая стадия
дала 78/78, всего 465 успешных прогонов. Первый preflight по трём baseline
конфигам завершился `unknown field comment` из-за сериализации wrapper вместо
per-symbol `SwingConfig`; результатов CSV не создал, логи сохранены в
`runs/preflight-failed/` и попытки не включены в счёт запусков. Повторный пул
с прямой схемой прошёл. Train-only победитель — qmc-086: RR 2.5, цель `target`
с cap 4R, срок 7 дней, lookback стопа 60 H4, buffer 0, коррекции требуют D
подтверждение (`correction_h4_confirm_without_opposing_zone=false`), часы
[8,12,16], боковик включён; стоимость и per-trade 1R не менялись. В train это
63.81R / закрытый DD 17.75R / 242 сделки против baseline 52.40R / 10.60R /
241: +11.40R, +21.76%, ниже целевого +25%; stage-one max-stat для 128 вариантов
дал условную familywise exceedance fraction 0.9440 (4720/5000), выше порога 5%.

Несмотря на неудачу stage-one max-stat, по протоколу выполнена ровно одна
диагностика; она не использовалась для замены победителя. На полной истории
baseline/qmc-086 net R 89.74/121.36 (+35.2%), однако continuous MTM DD с
фактической стоимостью 23.20/29.03R; просадка qmc-086 хуже на 5.84R. Интервал
пик→впадина по наблюдаемым минутным отметкам 149/441 дней (это не срок до
восстановления). На fresh-start проверке 2024–12.11.2026 net R 37.34/57.56
(+54.2%), но MTM DD 17.96/18.22R (хуже на 0.26R); пик→впадина 216/153 дней.
Максимум позиций/начального риска не вырос: 6→5 на полной истории и 6→4 на
fresh-start интервале. При этом fresh-period net R по EURUSD/GBPUSD/USDJPY
изменился 8.66/19.84/8.84 → −9.59/47.45/19.69R; эффект сосредоточен в GBPUSD,
а EURUSD перешёл в минус. Per-symbol full/fresh MTM DD baseline→qmc-086:
EURUSD 12.10/9.19 → 19.97/19.97R, GBPUSD 13.11/10.07 → 15.37/12.38R,
USDJPY 17.80/11.52 → 17.02/8.30R; per-symbol DD gate не пройден.

В fresh-period actual cost ×2/×3 net R baseline→qmc-086 составил 29.32→49.22R
и 21.87→41.58R; у qmc-086 EURUSD оставался отрицательным (−12.25R при ×2,
−14.58R при ×3). Из 13 заранее определённых одношаговых соседей 10 дали
положительный fresh uplift, медиана +19.43R, но три соседа дали отрицательный
uplift. В annual WFO каждый год выбирался только по предшествующим годам и
fresh-start запускался с января: baseline выбран для 2022–2024, qmc-117 для
2025–2026. Улучшение было только в 2025 (+6.62R), а в 2026 результат хуже на
0.83R; в обоих выбранных folds MTM DD вырос (2025: 9.36→9.75R; 2026:
10.56→11.95R), поэтому WFO gate также не пройден.

Итог: qmc-086 не достиг критерия значимого улучшения; он проходит net-R порог,
ограничение агрегатной экспозиции, fresh pair-majority, cost-stress и локальный
neighbor gate, но проваливает full/fresh и per-symbol MTM DD, WFO robustness и
selection-aware block-MC. `candidate-fixed.json` сохранён отдельно и помечен
`REJECTED_NON_PRODUCTION` в `candidate-disposition.json`; рабочий
`strategy/swing-rules.json` и application code не менялись. Хронологические
проверки свежим стартом не являются независимым holdout: та же MT5 M1 история
использовалась ранее. Все результаты — модель по наблюдаемым MT5 bid M1 данным,
не Upscale/ICE/live execution, не денежная доходность, маржа или рекомендация
включить правила.

Проверки анализа: Docker status files подтверждают 387/387 и 78/78 exit 0;
CSV-проверки подтвердили схемы всех 387 train-конфигов, порядок
signal≤fill≤exit и корректный source-grid start без carry-in в fresh/WFO.
Арифметическая сверка прошла: по full/fresh scope, пяти WFO folds и x2/x3
суммы pair net R равны агрегату и MTM closed-only; fresh inputs не содержат fill
до периода старта. Проверки `/tmp/forex-research-20261116-venv`:
`check-period-analysis.py` — 2/2 PASS; `python -m unittest discover -s tests
-p test_research_mark_to_market.py -v` — 6/6 PASS; строгая DST-конверсия и
синтетическая длительность 2 дня также PASS. Application code не менялся;
бэктесты и проверки не подключались к live-сервисам.

Подробные trial-метрики находятся в `stage1-summary.json`, итоговые pair/year,
MTM, WFO, costs и все promotion gates — в `diagnostic-summary.json`; зафиксированный
поиск и окружение — в `protocol.json`, `trial-pool.json`, `diagnostic-plan.json`,
`run-environment.json` и `manifest-sha256.json`.

Уточнение протокола аудита (итерация 2): бинарный SHA-256 берётся из

повторный выбор стратегии. Promotion threshold при baseline ≤0 требует
candidate ≥ baseline + max(25% × |baseline|, 0.25R); граница включительная.
Повторный analyzer на неизменённых CSV оставил победителя qmc-086, stage-1
63.8056R и семейный max-stat 0.9440; диагностический итог по-прежнему
`REJECTED_NON_PRODUCTION` с теми же шестью проваленными gate. LOO-проверка
закрытых train-сделок (net R / chronological closed DD, не MTM) сохранена в
`stage1-summary.json`: при исключении EURUSD/GBPUSD/USDJPY baseline даёт
31.677/13.946, 42.598/9.736, 30.533/8.531; qmc-086 — 27.420/21.429,
57.062/14.263, 43.129/15.740. При исключении exit-year 2022 остаётся
22.683/14.299 у baseline против 13.805/25.927 у кандидата; это показывает
зависимость train-преимущества кандидата от 2022. SHA release binary в

## Per-pair исследование swing из замороженного пула, 17.11.2026

Исследуется отдельный выбор параметров EURUSD, GBPUSD и USDJPY, без изменения
рабочего JSON. До расчётов зафиксирован
`reports/backtests/swing-pair-optimization-20261117/protocol.json`; он
переиспользует 128 ранее испытанных QMC-конфигураций, baseline и 387 train CSV,
без новых train-прогонов и новых параметров. Предыдущие manifest и версия этого
документа сохранены в `prior-snapshot`; исходные research artifacts не меняются.

Для каждой пары selector цензурирует закрытия после cutoff и выбирает только
кандидата со строго большим train net R и не худшими native-grid MTM DD и
экспозицией; одинаковые минутные entry/exit учитываются консервативно с входами
перед выходами, чтобы они не погашали максимум риска; если такого нет — baseline.
Выбор трёх direct configs фиксируется
одним research JSON до чтения primary/cost результатов. Primary fresh interval
2024-01-01–2026-11-12 и реальные replay costs x1/x2/x3 проверяются строго.
При каждом множителе на каждой изменённой паре и на combined portfolio
closed net R и terminal marked R должны оба строго превысить baseline;
engine-cost-included MTM DD, peak concurrent positions и peak open initial
risk не должны быть выше baseline. Неизменённая baseline-пара проходит по
равенству. Порог +25% не вводится.
Full-history остаётся описательным; та же история использовалась в прежнем
исследовании и не является pristine holdout.

WFO 2022–2026 выбирает пару отдельно только по предыдущим годам, каждый fold
запускается с пустым состоянием. Позиции оцениваются по последнему общему
наблюдаемому close до cutoff и учитываются один раз при сшивке reset-блоков;
полученная кривая — агрегированная переоценка независимых WFO блоков, не
реализованная continuous-live доходность. WFO gate требует, чтобы aggregate
terminal marked R независимых reset-блоков строго превысил baseline, а MTM DD

## Порядок работ

Для каждого изменения поведения: сначала документация по JSON, затем тест,
который воспроизводит отсутствие поведения или ошибку, запуск до реализации
с фиксацией причины падения, минимальная реализация и повторные проверки.
Все Rust-проверки и сборки выполняются в Docker с зафиксированными зависимостями.
Обычные тесты используют искусственные данные, управляемое время и подменяемые
сервисы; не требуют ключей, живого рынка или платных вызовов.

### 1. Контракт JSON

Проверить загрузку текущего файла, поля, перечисления, ссылки, диапазоны,
неизвестные/повторные ключи и ID правил. Карта блоков должна ссылаться на реальные
пути текущего JSON. Перестановка правил не должна менять их смысл.
Значения RR, ATR, сроки и шаги цены читаются из JSON без противоречащих копий.
Неподдерживаемое значение отклоняется явно, файл не заменяется данными из SQLite.

**Приёмка:** `check-config` и `describe-config` для текущего JSON, негативные
проверки контракта и согласованности ссылок. Относится к R2, R8.

### 2. Свечи, источники и состояние

Привести импорт и текущий поток к общей сетке `candles`; сохранить источник,
единицы, UTC-время и признаки пропусков. Проверить изоляцию инструментов,
достаточность свечей и восстановление после перезапуска. Правила хранятся только
в JSON; SQLite содержит состояние и хеш, но не копии правил.

**Приёмка:** границы H4/D/W зимой, летом и при DST; котировка ровно на границе;
неполные и незакрытые бары; отсутствие выдуманных минут; повтор события и импорта;
конфликт данных; сохранность состояния и комментариев после перезапуска.
Загрузка предыдущих свечей рассчитывает зоны и направление без прошлых сигналов.
Сопровождение выданного сигнала не прекращается из-за нехватки свечей для нового.
Относится к R2, R7, R8, R11.

### 3. Торговая логика

Проверить реализацию блоков `policies.zones`, `policies.plans`, `policies.targets`,
`policies.execution` и `policies.positions` по текущему JSON. Не добавлять торговых ограничений из прежних
описаний или исследовательских скриптов.

Для правил «свинг» отдельно проверять срок Pending-заявки на граничном дневном
закрытии, отсутствие позднего исполнения, сопровождение Active, отключение файла
и пары через снимок после перезапуска, режим только сопровождения опубликованных
Pending/Active и повторное включение без потери штатной публикации основного движка.
При одном наблюдаемом тике, который исполнил опубликованную лимитку и достиг
выхода, проверять сохранённые события исполнения и выхода в правильном порядке.
Отдельно проверить первый тик, который закрывает свечу, создаёт и исполняет
лимитку, оставляя сделку Active: два события limit → fill. Затем проверить
вариант с выходом на том же тике: limit → fill → exit. В обоих случаях тип
ордера сохраняется при совпавшем времени, лимитное сообщение показывает исходный
уровень/RR до издержек, fill — фактическую цену/RR с издержками; повтор и restart
не дают дублей. Проверить на покупках и продажах при ненулевом cost.

### 4. Telegram и изменение правил

Сохранить приём ответов всех участников группы, текстов и изображений,
последовательный OpenAI-разбор и надёжную запись JSON. После правки пересчитывать
только `wait_confirm`/`wait_entry`; уровни `setup`/`active` сохранять по
`policies.positions.rule_update`.

**Приёмка:** ответы разных авторов по очереди, изображения и уточнения,
невалидный ответ API, недоступность OpenAI с последующей обработкой очереди,
продолжение сигналов при сбое API, ошибка записи JSON, сбой до/после rename,
повтор update и перезапуск. Проверить неизменность входа/стопа/цели/тейка
`setup`/`active` после правки и неизменность завершённых результатов.
Проверить привязки сообщений и доставку после сбоя без повторного применения
правил. В API передаётся только необходимый контекст, расход сохраняется.
После торговой правки проверять фактически пересчитанные условия wait-планов,
их прежние ID и оставшийся срок; сообщения должны содержать ID операции и плана,
направление, применимые новые условия подтверждения для wait_confirm или
актуальные условия входа для wait_entry. Проверить повторный цикл A→B→A→B с
доставкой между изменениями, перезапуском и совпадением JSON правил со снимком;
ключи outbox различают разные операции над одним планом. Уровни setup/active и
завершённых результатов не меняются. Правка только comment не пересчитывает планы.
Относится к R3–R6, R8–R10.

### 5. Чистая БД и локальная поставка

Проверить создание чистой SQLite v4 по пути data/signals.sqlite и восстановление
нового состояния после перезапуска. Старые БД и архивы не переносить,
не изменять и не подключать; старые схемы SQLite отклоняются без миграции.
Переход версии календаря поддерживаемого снимка v4 проверять отдельно: он
восстанавливает расчётный контекст из минут и сохраняет сигналы и связанные
данные. Исторические результаты и исходные данные не переписывать.

После целевых тестов выполнить полный Rust-набор, rustfmt check и Clippy
с `-D warnings` в Docker, собрать Linux x86_64 и выполнить автономный smoke-test
на новой тестовой БД. Проверить содержимое поставки; не подменять рабочие БД и секреты.
Сообщение запуска и два диагностических лога проверяются автономно.

**Приёмка:** зафиксированные результаты проверок и контрольная сумма нового
бинарника. Это подтверждает локальную поставку, не установку на сервере.
Относится к R1, R4, R6, R8, R10.

### 6. Живые подключения и сквозная приёмка

Отдельно проверить историю индекса Upscale и её стык с текущими снимками,
разрывы и переподключение. Пройти путь сигнал → комментарий со скриншотом →
изменение JSON → пересчёт ожидающего плана при сохранении уже выданных уровней →
наблюдаемый результат сигнала. Проверить уведомления о сбоях и восстановление.
При необходимости использовать явно обозначенный тестовый сигнал.

Автономный `scripts/research_mark_to_market.py` должен требовать у результатов
непустой список provenance по каждому символу и проверять каждую запись как
объект с непустым строковым `source`; все источники должны совпадать между собой
и с единственным источником минут в SQLite. Тесты отклоняют отсутствие списка,
пустой список, malformed/non-object, blank/whitespace и несовпадающие источники;
несколько корректных записей одного источника принимаются. Успешный отчёт хранит
источник и coverage.
Это проверка исследовательских данных, а не критерий корректности стратегии.

### Итерация реализации 2: валидация параметров и смешанных семей

покрывают объединение используемых leaf-полей, а обязательность полей
проверяется по десериализации и `SwingConfig::validate` для каждого выбранного
семейства. Рабочий legacy JSON без явного family остаётся совместимым.

Терминальный signal ID остаётся зарегистрированным после закрытия или отмены.
Перед прогревом на новой конфигурации runtime учитывает подтверждённые signal ID
снимка и ещё не доставленные outbox-сообщения, не меняя очередь и её порядок.
RED должен проверить повторное обнаружение terminal-трейда после delivered и
pending события, с рестартом и сменой конфигурации, отсутствие повторного
сообщения/сопровождения, а также чтение legacy snapshot без `retired`.
Отдельный pending-only сценарий оставляет undelivered и событие открытия, и стоп;
`known` пуст в исходном и восстановленном снимках. Он проверяет неизменность
обоих сообщений и отсутствие нового сообщения/сопровождения после прогрева.

Legacy-поведенческие тесты используют закреплённый fixture, не рабочий JSON.
Рабочий JSON проверяется отдельным schema/validate тестом. Смешанные документы
проверяются с `trend_pullback` у EURUSD и отдельно у GBPUSD; комментарии покрывают
объединение ключей, а пропуск обязательного ключа каждого семейства отклоняется.

Для сообщения о событии runtime передаёт фактический UTC timestamp Tick; source
grid остаётся только входом расчётного движка. RED/GREEN проверяет точные
RFC3339 строки для зимнего и летнего события от retired экземпляра, чтобы
переход DST не сдвигал показываемое время.

### Поисковый раунд 2: ограничение перекрытия `trend_pullback`

Первый train-раунд завершился без прошедшего tuple: `selected_id=None` записан
в его train-only candidate-freeze record. Его 39 replay и полные 2 197 score
сохраняются как завершённая неудачная попытка; primary/cost evaluation для него
не запускается. Причина следующего раунда — наблюдаемое накопление коррелированных
TP позиций, а не изменение критериев доходности.

В каждом из 12 `trend_pullback` вариантов второго раунда явно задаётся
`max_open_positions=1`; baseline остаётся без этого поля и не меняется. Каждая
принятая сделка сохраняет 1R. Runtime считает Pending/Active позиции инструмента
в текущем и retired экземплярах. Когда лимит заполнен, новый подтверждённый
сигнал пропускается без очереди, но EMA/context продолжают обновляться. Счёт
проверяется до минутной обработки выходов; выход в ту же минуту освобождает
слот только для последующего сигнала. Старые позиции сопровождаются с прежними
уровнями.

До нового freeze выполняются Docker RED/GREEN на cap: второй сигнал при полном
лимите не создаёт сделку, сигнал после освобождения слота допускается, EMA
обновляется пока вход заблокирован, проверяются обе стороны, совпадающие
времена входа/выхода, рестарт, смена конфигурации с сохранённой Pending заявкой
и Active позицией, исполнение заявки без двойного счёта слота,
отклонение `null`, строки, дроби, нуля и отрицательного cap, принятие `1`, а
также совместимость прежнего JSON/snapshot без поля.
При смене cap на значение меньше текущего числа Pending/Active Runtime сохраняет
их всех и не создаёт новые входы до освобождения места; принудительное закрытие
или отмена прежних уровней запрещены.
Дополнительная проверка NS-03 использует реальные `Runtime::tick` H4 закрытия:
без внешнего слота сигнал создаёт сделку; retired Pending и Active блокируют
такой же подтверждённый вход, блокировка переживает restart, а после терминального
выхода следующий новый pullback/recovery сигнал снова допускается. Изолированная
мутация передачи `external_open_positions` должна сделать этот тест красным.
Рабочий торговый JSON остаётся baseline.

Сравнительные метрики используют фактические UTC причинные поля event ledger:
`observed_at_utc`, `admitted_at_utc`, `executed_at_utc`, `exited_at_utc`.
Compatibility `signal_t`/`fill_t` и raw CSV сохраняются отдельно; например
legacy `fill_t=bar.end` не переносит вход назад. Live response получает один
`observed_at_utc_ms` от injected system UTC wall clock сразу после полного
`markets()` ответа; это Unix milliseconds UTC и один timestamp для всех quotes
ответа. Batch ID/time durable inbox сохраняет до обработки, retry использует
сохранённое значение. В joint replay полная строка M1 `[start_utc_ms,end_utc_ms)`
становится доступной на исключительной правой границе `end_utc_ms`; полученные
из строки admission/fill/exit имеют это causal time. Сохраняются исходный
интервал и legacy timestamps. V3 модель цен и последовательности сохраняется:
рыночный fill по предусмотренной движком цене с adverse cost, stop-before-target
по полному M1 high/low, прежние fill levels. Новый market fill по open и отдельное
исполнение stop/target по open не добавляются. OHLC не раскрывает время точного
intraminute касания. Полная M1 строка, доступная ровно на cutoff, не входит в
`[start,cutoff)`; terminal mark берётся по последней доступной строке до cutoff,
future exit цензурируется. Raw CSV byte parity и новые causal metrics проверяются
раздельно; baseline пересчитывается тем же accounting, прежние числа не
переносятся автоматически.

Два watermark независимы. `source_watermark_utc` — максимум processed допустимых
source timestamps, используемый только для межпарного source-late. Его значение
сохраняется до batch; все quotes response классифицируются относительно этого
предbatch watermark, затем он обновляется максимумом допустимых timestamps.
`observed_watermark_utc` — максимум причинных событий; только его UTC minutes
управляют terminal reserve и slot release. Source time не сравнивается с observed
watermark. Retry использует captured receive time.

Один live `markets()` ответ — одна observed-minute группа и одна атомарная
transaction, даже когда source timestamps пересекают минутную границу. Фазы
одного response: occupancy, admission всех intents по `(observed_at_utc,
ASCII symbol, intent_key)`, затем исполнения и exits. Exit не освобождает slot
для другого входа этого ответа. В joint replay строки доступны по возрастающей
правой границе, для каждой observed-minute группы фазы повторяются заново.
Пример A exit 10:00 / B intent 10:00 reject / C intent 10:01 admit относится к
разным causal replay times. Эквивалентность при разбиении гарантируется только
при тех же captured times и порядке; если split меняет receive time, обещания
равного live результата нет. Batch сохраняет все изменения атомарно.

`intent_key` остаётся versioned tuple
`(config_generation:u64, family_code:u8, plan_id:UTF-8 bytes,
source_event_ms:i64, direction_code:u8, intent_ordinal:u64)`; numeric сравнения
числовые, strings сравниваются bytewise, enum codes фиксированы. Ordinal
монотонен на config generation/symbol/family/plan и различает corrections с
совпавшим внешним ID. Общий tie-break — `(observed_at_utc, ASCII symbol bytes,
intent_key)`, без hash-map iteration; внешний ID неизменен.

`source_watermark_utc` определяет late quote без смешивания часов; source-late —
строго `source_timestamp < source_watermark_utc` предbatch. При включённом
portfolio cap такая quote не создаёт admission; без общего cap late-status только
диагностический и не блокирует локально допустимый entry. В обоих режимах
локально допустимая не повторная quote продолжает сопровождать existing
Pending/Active, включая retired; сохраняются per-pair out-of-order, dedup и
per-symbol TP cap. Вызванные quote fill/exit получают captured observed time, не
меняют прошлую кривую; slot освобождается не раньше следующей observed-minute.
Обычная delivery latency не делает quote late из-за сравнения разных clocks.

Старый snapshot восстанавливает source watermark из сохранённых source
timestamps. Если observed watermark отсутствует, нельзя использовать `Tick.millis`
как receive time. При первом batch сохранить его captured observed time как
`bootstrap_observed_at_utc_ms`; старый inbox без timestamp использует фактическое
время начала первой обработки. Retry сохраняет то же время. Occupancy берётся из
current/retired Pending+Active без изменения trade conditions. При cap admission
блокирован всю первую bootstrap observed-minute, но management/fill/exits старых
позиций работают сразу; admission снова доступен только со следующей observed
минуты при свободном бюджете. Bootstrap time/barrier сохраняются через restart.
Без общего cap barrier не блокирует local admission.

NS-05 peak open initial risk суммирует только исполненный risk Active-сделок от
`executed_at_utc` до `exited_at_utc`, с entry-before-exit при равном времени.
Pending reserve занимает slot, но не open risk; Pending→Active учитывает risk
один раз. Pending + Active + terminal reserves — отдельный слотный инвариант,
который не заменяет NS-05. При config switch `switch_at_utc_ms` — миллисекунда
UTC успешного atomic commit с новым `config_generation`; source grid конвертируется
явным DST-aware mapping. Бары новой стратегии с `bar.end_utc <= switch_at` —
только контекст, даже если обнаружены поздно; новые intents требуют
`bar.end_utc > switch_at` и `observed_at_utc > switch_at`. Retired trades идут по
прежним условиям и остаются в общем budget. Cold start — совместный warmup одним
coordinator; старые snapshots восстанавливают reservations из current/retired
Pending/Active. Legacy rejected plan остаётся `WaitEntry`, trigger помечается,
очередь не создаётся; retry только на новом подходящем торговом событии. Range
reject не создаёт Trade/`Sweep`, не меняет stop counter и не пробует opposite
side на том же баре.

Перед кодом обязательны Docker RED: M1 open выше target при low, коснувшемся
stop, сохраняет V3 stop-first по high/low; M1 строка, доступная ровно на cutoff,
исключена; V3 market price/adverse cost/fill levels сохраняются. Raw CSV parity
проверяется отдельно от causal baseline metrics. Один live ответ с source times
по разные стороны минуты остаётся одной observed-minute group без early release;
source-late определяется по предbatch source watermark; обычная latency не
смешивает clocks. Locally valid source-late quote сопровождает current/retired
позиции и исполняет stop на captured observed time; rebound не отменяет выход.
Новый admission от этой quote блокируется capped, но разрешён uncapped; проверить
capped/uncapped и restart с одинаковым management. Slot release — не раньше
следующей observed-minute. Replay 10:00/10:01 проверяет A/B/C. Также нужны
Pending slot без open risk и одно увеличение при Active fill; correction tie-break
после restart; config switch через gap и поздно обнаруженный H4; старый snapshot
без обоих watermark, повторный restart и устойчивый bootstrap barrier; одинаковый
locally valid source-late H4 intent разрешён uncapped и блокируется capped.
NS-05/train-gates не меняются. Это отложенный дизайн, не разрешение кода или
исторического поиска по D4. Частичный work-in-progress не является поддерживаемой
возможностью общего лимитера; этот этап остановлен до отдельного нового решения.
