# Требования к Telegram-боту Forex

Единственный источник торговых правил — локальный `strategy/fvg-bot-rules.json`,
торговая редакция `agreed-v4`, формат v2. При расхождении торгового описания с JSON исправляется
документация. Рабочий файл исключён из Git; начальная конфигурация — [example.json](../../example.json).
Этот документ задаёт продукт и поясняет действующие правила; [архитектура](architecture.md)
описывает устройство, [план](development-plan.md) — работы и результаты проверок.
Наличие требования не означает, что оно уже реализовано и проверено.

## Продукт

| ID | Требование | Основание |
|---|---|---|
| R1 | Бот написан на Rust под Ubuntu 26.04.1 LTS. Разработка и сборка выполняются в Docker; на сервере готовый бинарник запускается под systemd. | Прямое указание пользователя при запросе плана и подтверждённый выбор окружения разработки и запуска. |
| R2 | Стратегия задаётся рабочим strategy/fvg-bot-rules.json с уточнениями пользователя. Поддерживаемые правила меняются через JSON без переписывания бота. | Уточнение «Я дам тебе готовый json с правилами» и принятый подход конфигурации. |
| R3 | Пользователь создаёт Telegram-группу, добавляет бота; бот присылает туда торговые сигналы. Формат: валютная пара, покупка или продажа, время, вход, стоп, цель, RR и краткое объяснение по правилам JSON. | Исходный порядок работы, пункты 1–3; формат сигнала подтверждён пользователем. |
| R4 | Участники настроенной Telegram-группы комментируют сигнал текстом и скриншотами графиков ответом на сообщение бота с сигналом в Telegram. Все участники группы имеют равные права изменять правила через комментарии. Текст и изображения сохраняются с привязкой к этому сигналу и используются при API-разборе с первого выпуска. | Исходный порядок работы, пункты 4–5; уточнение «Нужны сразу скриншоты»; подтверждены отправка ответом на сигнал и равные права обоих авторов. |
| R5 | Комментарий запускает обработку через OpenAI API; изменения правил применяются сразу по результату обработки, без отдельного подтверждения. Каждый ответ любого участника группы считается новым дополнением и обрабатывается последовательно, в порядке поступления, с учётом уже применённых изменений. Однозначное новое дополнение может изменить ранее установленное правило без согласования между авторами. При неоднозначности самого комментария бот уточняет его смысл в чате и не применяет неоднозначное изменение. После изменения JSON бот кратко сообщает в чат, что изменил и по какому комментарию; пересчитывает планы wait_confirm/wait_entry по новым правилам и сообщает новые условия в чат. | Уточнения «применять изменения сразу после комментария», заменяющее суточный цикл, и «каждый ответ новым дополнением, обрабатываем их по-очереди». |
| R6 | При недоступности OpenAI бот уведомляет чат и продолжает рассчитывать и присылать сигналы по действующему JSON, если котировки и Telegram доступны. После восстановления OpenAI автоматически обрабатывает накопившиеся за время сбоя комментарии. | Прямое требование после создания API-ключа; подтверждено продолжение сигналов по действующим правилам при сбое OpenAI и автоматическая обработка накопленных комментариев после восстановления. |
| R7 | Серверный бот рассчитывает текущие сигналы. Отдельный локальный бэктест оценивает переданный JSON на архивных тиках и выпускает PDF; общий движок используется обоими приложениями. | Прямое уточнение пользователя. |
| R8 | Факты и добавленные разработчиком допущения не смешиваются. Неизвестные правила не додумываются незаметно. | Уточнения об отделении реальных данных от собственных ограничений. |
| R9 | Экономно расходовать токены API: не раздувать промпты, передавать только необходимый для разбора комментария контекст. | Прямое требование пользователя о расходе лимита. |
| R10 | После отправки сигнала бот отслеживает достижение его стопа и цели по котировкам и сообщает результат в чат. При обновлении правил опубликованные setup/active сохраняют исходные вход, стоп, структурную цель и тейк; пересчитываются только wait_confirm/wait_entry. | Отслеживание подтверждено пользователем; сохранение уровней задано policies.positions.rule_update рабочего JSON. |
| R11 | При потере котировок бот уведомляет чат и приостанавливает новые сигналы до восстановления данных. | Пользователь подтвердил поведение при потере котировок. |

Бот выдаёт сигналы EUR/USD, GBP/USD и USD/JPY и отслеживает их по котировкам. Он не отправляет
реальные ордера брокеру. «Вход», «стоп» и «тейк» в сообщениях означают наблюдаемые
события сигнала, а не подтверждение исполнения на брокерском счёте.

Согласованы технические решения: SQLite, Telegram long polling, последовательная
очередь обработки изменений, повторы запросов и хранение времени в UTC.
Также согласовано: до лимитного входа достижение стопа/цели проверяется
по выбранной основе цены: в текущем режиме index — по одной индексной цене.

## Торговые правила

Значения и идентификаторы реализованных политик читаются из JSON; таблица показывает их назначение.
Числа ниже описывают текущую редакцию, а не независимые константы программы.

| Предмет | Правило и источник в JSON |
|---|---|
| Инструменты | `instruments`: EURUSD, GBPUSD, USDJPY. Общая стратегия, отдельные свечи, планы, сигналы и шаг цены для каждой пары. |
| Свечи | `candles`: закрытые index-свечи, America/New_York с DST; H4 01/05/09/13/17/21, D1 17:00, W с воскресенья 17:00. Время событий хранится в UTC. |
| Предыдущие свечи | `context`: до W=160, D=400, H4=400; минимумы W=6, D=30, H4=30. Используются для расчёта зон, фракталов и направления каждой пары. |
| Доступное время | `policies.trade_window`: по умолчанию все доступные торговые часы (`session_filter=false`). При `session_filter=true` входная зона H4 выбирается только на закрытии свечей H4, час закрытия которых (America/New_York) перечислен в `entry_h4_close_hours`; на остальных закрытиях план остаётся в ожидании входа и может получить зону на следующем разрешённом закрытии. Подтверждение планов, отмена, истечение срока и сопровождение уже опубликованных сигналов от фильтра не зависят. |
| Зоны и направление | `policies.zones` и `policies.fractals`: FVG, гэпы, реакции, инверсии, фракталы и состояния тренда. Гэп образуется разрывом close/open и далее используется как FVG. |
| ATR и рабочая зона | `parameters` и `policies.zones`: период ATR, минимальные размеры зон, выбор ATR и зоны. Рабочая зона — с самой свежей свечи образования; при равенстве — ближайшая к цене. |
| Планы | `policies.plans`: W задаёт направление, D — планы, H4 — подтверждение, вход и сопровождение. Без недельного тренда дневные планы не строятся. `disabled_rules` — необязательный список отключённых правил; отсутствие поля эквивалентно `[]`. |
| POI | Четыре дневных правила correction/continuation используют вызвавшую правило дневную зону. `W_point_A` использует недельную зону. |
| Цели | `policies.targets`: ближайший подходящий неснятый фрактал или FVG, для FVG — ближняя граница. D POI → D; W POI → W либо более близкая D-цель с RR не ниже `rr_min`. Фиксированная цель без структуры запрещена. |
| Стоп | `policies.plans.stop`, `parameters.stop_fallback_h4_bars`: последний подтверждённый H4-фрактал с защитной стороны зоны; при отсутствии — экстремум последних 10 H4. Буфер задаётся `stop_buffer_atr`, ATR — последней закрытой H4. |
| Вход | `policies.execution`: первая доступная котировка после подтверждающей H4; при RR ≥ `rr_min` — рыночный, иначе лимитный по политике `solve_rr_min_keep_stop_target` с сохранением стопа и цели. |
| Потолок RR | `rr_max_correction` для коррекции, `rr_max_trend` для trend/continuation. Сейчас оба равны 10, `rr_min` равен 2; значения настраиваемые. `policies.targets.mode=structural_only`. |
| IFVG | `ifvg_entry`, `ifvg_max_zone_age`, `ifvg_limit_range` задают включение входа, окно образования встречной зоны и допустимый диапазон лимитной цены. |
| Отмена и срок | `policies.execution.pending_cancel_on` и условия отмены; `plan_days` действует на `plan_days_statuses`. Отменённый вход позже не активируется. |
| Порядок событий | `policies.execution.event_order`: только наблюдаемые котировки. Неизвестный путь цены внутри свечи или пропуска не додумывается. |
| Параллельные планы | `policies.positions`: независимые сетапы ведутся отдельно, повтор одного сетапа не создаёт дубль. Смена плана не прекращает сопровождение его активного сигнала. |
| Суммарный риск | `max_open_risk_r=null` означает отсутствие лимита. Для заданного лимита JSON определяет `risk_per_trade_r`, `risk_counted_statuses`, `risk_queue_order`; поддержка этого варианта отмечается в плане. |
| Изменение правил | `policies.positions.rule_update`: пересчитываются `wait_confirm` и `wait_entry`; `setup` и `active` сохраняют исходные уровни до стопа, тейка или отмены. Завершённые результаты не переписываются. |
| Отключённые возможности | `policies.modules.range_trading`, `daily_point_a`, `weak_correction` выключены. Их наличие в JSON не означает отдельной задачи включить их. |

Загрузка предыдущих свечей не создаёт прошлые планы, входы и сообщения.
Отдельного переключателя исторического прогона в конфигурации нет.

## Правила «свинг» (перенос проверенного черновика)

Отдельный набор правил, перенесённый один к одному из исследовательского черновика.
Действующие правила выше он не меняет. Состав: планы «тренд» и «коррекция», вход,
стоп, тейк и исполнение; торговля в боковике; выход по индексу доллара.

| Тема | Правило |
|---|---|
| Свечи | H4, D и W по сетке источника; неделя — с понедельника 00:00 времени сетки. Свечи без котировок не создаются. |
| Фрактал | Свеча, у которой максимум (минимум) выше (ниже), чем у обеих соседних; известен после закрытия следующей свечи. Снят, когда более поздняя свеча прошла его цену. |
| Зона (FVG) | Разрыв между первой и третьей свечой тройки, без минимального размера. Жива, пока свеча не закроется за дальней границей; это закрытие — инверсия зоны. |
| Структура | Вверх: последние два верхних и два нижних фрактала последовательно выше; вниз — последовательно ниже; иначе структуры нет. |
| ATR | Среднее (максимум − минимум) последних `atr_period` свечей. |
| План «тренд» | На закрытии недели при недельной структуре: последняя живая недельная зона по структуре, лежащая за ценой закрытия, затронута этой неделей, и есть ближайший неснятый недельный фрактал по ходу. Цель — этот фрактал. Подтверждение — на H4. |
| План «коррекция» | На закрытии недели при недельной структуре: неделя прошла недельный фрактал по ходу структуры, которого предыдущая неделя не проходила. Направление — против структуры, цель — ближняя граница последней живой недельной зоны по структуре. Подтверждение — на D; если между последним дневным закрытием и целью нет живой дневной зоны против плана — на H4. |
| Повтор плана | План с тем же видом, направлением и точкой отсчёта не создаётся, пока прежний не завершён. |
| Подтверждение | На таймфрейме подтверждения закрылась свеча, образовавшая зону по плану или инвертировавшая зону против плана. |
| Вход | После подтверждения: закрылась свеча H4, образовавшая зону по плану, и час её закрытия входит в `entry_close_hours`. |
| Стоп | Ближайший фрактал H4 за защитной стороной (за меньшим из цены входа и границы зоны для покупки, зеркально для продажи) среди последних `stop_lookback_h4_bars` свечей; если его нет — дальняя граница зоны. Отступ `stop_buffer_atr` × ATR(H4). |
| Тейк и способ входа | Если до цели не меньше `rr_fixed` риска — вход по рынку; тейк на `rr_fixed`, а при `take_profit=target` — на цели, но не дальше `rr_target_cap`. Если меньше — лимитная заявка в точке, от которой до цели ровно `rr_fixed` при том же стопе; если эта точка хуже текущей цены, сделки нет. |
| Издержки | Цена исполнения хуже на `cost` в сторону сделки. |
| Лимитная заявка | Исполняется в любое время при касании цены. Снимается, если цена дошла до тейка раньше входа или план завершён. |
| Выход | Стоп или тейк; при обоих в одной минуте — стоп. Результат стопа −1R. |
| Срок и отмена плана | План без открытой сделки, включая план с ожидающей лимитной заявкой, завершается на `plan_days`-м дневном закрытии после создания. На этой границе заявка отменяется до проверки исполнения по следующей котировке. После исполнения срок плана больше не закрывает сделку. «Тренд» завершается недельным закрытием за зоной, «коррекция» — дневным закрытием за ценой фрактала. |
| Начало работы | До `start` свечи только накапливаются; планы и сделки не создаются. |
| Свечи бота | В боте и в бэктесте по базе правила получают свечи, которые строит бот (`feed::Aggregator`), включая неполные — с разрывом котировок или отключением внутри. Неполная свеча строится только из пришедших котировок, пропуски не заполняются. Правила основного движка по-прежнему получают только полные свечи. Время свечей переводится в сетку источника: время Нью-Йорка + 7 ч (00:00 сетки — 17:00 Нью-Йорка). Цены — индексные цены базы, делённые на 1 000 000. |

Торговля в боковике (`range.enabled`):

| Тема | Правило |
|---|---|
| Когда ищется диапазон | На каждом закрытии H4, если закрыто больше `range.min_h4_bars` свечей H4, диапазона сейчас нет и ATR(D) больше нуля. |
| Диапазон | Самый длинный отрезок из последних закрытых H4 (без текущей), от `range.window_min` до `range.window_max` свечей, у которого высота (максимум − минимум) не больше `range.height_max_atr_d` × ATR(D). Высота должна быть не меньше `range.height_min_atr_d` × ATR(D). Границы — максимум и минимум отрезка. |
| Импульс перед диапазоном | `range.impulse_bars` свечей H4 прямо перед отрезком прошли не меньше `range.impulse_min_atr_d` × ATR(D) и не меньше `range.impulse_min_ratio` × высоты диапазона. Иначе диапазон не принимается. |
| Один диапазон на импульс | Импульс засчитывается, только если начался больше чем через `range.impulse_bars` свечей после начала импульса предыдущего принятого диапазона. |
| Конец диапазона | Закрытие H4 дальше `range.break_fraction` × высоты за любой границей. После закрытия сделки в боковике (тейк или стоп) диапазон ищется заново. |
| Сигнал продажи у верхней границы | Закрытие H4 внутри диапазона и одно из двух: максимум свечи выше границы не меньше чем на `range.wick_min`, либо предыдущая свеча закрылась выше границы. Покупка у нижней — зеркально. Сначала проверяется верхняя граница; за одно закрытие — не больше одной сделки. |
| Ограничения | Одновременно не больше одной сделки в боковике (с заявкой). От одной границы диапазона — не больше `range.max_stops_per_border` стопов. Вход — только на закрытии H4 из `entry_close_hours`. |
| Стоп | За экстремумом девиации — максимумом (минимумом) текущей и предыдущей свечи — с отступом `stop_buffer_atr` × ATR(H4). |
| Тейк и способ входа | Цель — противоположная граница. Если до неё не меньше `rr_fixed` риска — вход по рынку, тейк на `rr_fixed`. Иначе лимитная заявка в точке, от которой до цели ровно `rr_fixed`; точка должна лежать внутри диапазона. Исполнение, издержки и выход — как у остальных сделок. |

Выход по индексу доллара (`reference_exit`, для инструмента, у которого задан знак):

| Тема | Правило |
|---|---|
| Индекс | Синтетический индекс доллара по формуле ICE: 50.14348112 × EURUSD^−0.576 × USDJPY^0.136 × GBPUSD^−0.119 × USDCAD^0.091 × USDSEK^0.042 × USDCHF^0.036. Открытие и закрытие минуты — по открытию и закрытию пар; максимум и минимум — по тем экстремумам пар, которые двигают индекс в нужную сторону. Минута индекса есть, только если есть эта минута у всех шести пар. |
| Расчёт по индексу | По минутам индекса работает отдельный экземпляр правил «свинг» со своими параметрами. Он не торгует, а только отмечает события: цель плана «тренд» или «коррекция» достигнута (первое касание, время — минута касания, направление — направление плана), открыт вход в боковике (время — закрытие свечи, направление — направление входа), план подтверждён (время — закрытие свечи). |
| Знак | Направление индекса, которое соответствует сделке по инструменту: −1 для EURUSD (индекс вниз — евро вверх). |
| Выход | В каждой минуте до исполнения заявок открытая сделка закрывается по закрытию минуты, если среди последних `reference_exit.recent_events` событий индекса, известных к этой минуте, есть «цель достигнута» или «вход в боковике» с направлением сделка × знак и временем строго после исполнения сделки и не позже этой минуты. Результат — по фактической цене; закрытие сделки в боковике завершает диапазон, но стопом не считается. |

### Исследовательское расширение правил по инструментам

Текущий swing остаётся совместимым семейством `legacy_swing`. Для нового
исследовательского семейства `trend_pullback` его параметры задаются отдельно
для каждой пары; рабочий JSON без явного выбора семейства продолжает означать
legacy swing. Неизвестное семейство и неполные параметры нового семейства
отклоняются. Переключение пары не меняет конфигурации остальных пар.

`trend_pullback` — исследовательское правило, а не ранее согласованное
пользовательское условие. Оно использует только закрытые H4 свечи, построенные
тем же агрегатором и в той же временной зоне, что и swing. Быстрая и медленная
EMA считаются по H4 close; каждая EMA инициализируется средним первых `period`
закрытий, далее `EMA[t] = alpha*close[t] + (1-alpha)*EMA[t-1]`,
`alpha=2/(period+1)`. Пока нет полной истории для медленной EMA, сигналов нет.
В JSON инструмент сохраняет все общие swing execution-поля и задаёт
`"family": "trend_pullback"` вместе с обязательным
`"trend_pullback": {"fast_ema_bars": ..., "slow_ema_bars": ...}`.
Legacy задаётся либо отсутствующим `family`, либо явным
`"family": "legacy_swing"`; в обоих случаях параметры
`trend_pullback` отсутствуют. У `trend_pullback` поле параметров обязательно;
несогласованные сочетания и неизвестные поля отклоняются.

`cost` во всех семействах — конечное неотрицательное число в единицах цены;
отрицательные и неконечные значения конфигурации отклоняются. Для legacy
семейства это общее ограничение не меняет расчёт уровней и исполнение. В
`trend_pullback` дополнительно проверяются конечность рассчитанного входа,
стопа, риска и цели, строго положительные цены входа/стопа/цели и
положительный риск в направлении сделки. Сделка не создаётся при переполнении
или неположительном ценовом уровне. Для этой семьи нет произвольного верхнего
предела `cost`: проверяются конкретные рассчитанные уровни. При сравнении
×1/×2/×3 исходный положительный `cost` умножается на коэффициент; обе модели
используют одинаковый коэффициент и единицу риска.

Для смешанного файла инструментов `comments` поясняет объединение всех leaf
ключей, используемых всеми парами. Семейство определяет свои обязательные
поля: у legacy поле `family` необязательно, а `trend_pullback` запрещено;
новое семейство требует оба поля и оба EMA-параметра. Сначала десериализуется
соответствующая конфигурация, затем выполняется семейная и общая валидация;
параметр другой семьи или пропущенный обязательный параметр отклоняется.
Комментарии не заставляют разные пары выбирать одинаковую стратегию.

Во втором поисковом раунде новый `trend_pullback` JSON явно задаёт
`trend_pullback.max_open_positions: 1`. Это положительное целое; ноль,
отрицательное, `null` или значение другого типа отклоняется. Поле остаётся
необязательным при чтении прежних JSON и snapshots: если ключ отсутствует,
сохраняется прежнее
неограниченное поведение. Параметр действует только на `trend_pullback`; legacy
не ограничивается. Каждая допущенная сделка сохраняет исходный риск 1R.

Лимит считается по инструменту, а не по экземпляру стратегии. Pending и Active
сделки текущей и retired-конфигураций занимают место до отмены или закрытия;
их существующие уровни и сопровождение не меняются. Если при смене конфигурации
занятых слотов уже больше нового лимита, позиции и заявки не отменяются и не
закрываются принудительно; новые входы блокируются до освобождения слота.
Переход Pending → Active сохраняет тот же слот, отмена заявки или завершение
сделки освобождает его в принятом порядке событий. При полном лимите новое
подтверждённое событие `trend_pullback` пропускается, не ставится в очередь и
не исполняется позже. EMA и остальной контекст обновляются и во время блокировки. Допуск
проверяется до обработки выходов текущей минуты: позиция, закрываемая в той же
минуте, освобождает место только для следующего сигнала.

Покупка возникает на закрытии H4 `t`, если быстрая EMA выше медленной как на
предыдущем закрытии, так и сейчас; предыдущий H4 close был не выше своей
быстрой EMA, а текущий close выше своей быстрой и медленной EMA. Продажа —
зеркально: быстрая EMA ниже медленной на предыдущем и текущем закрытиях,
предыдущий close не ниже быстрой EMA, текущий close ниже обеих EMA. Требование
уже установленного тренда перед возвратом исключает начальный cross из боковика.
Так
подтверждается возврат по тренду после отката через среднюю; решение не
использует незакрытую свечу или её будущие экстремумы. Один сигнал имеет
стабильный ключ из пары, семейства, направления и времени закрытия H4.

Сигнал становится рыночным входом при первом наблюдении закрытия сигнальной H4
свечи в ту же минуту, что и её `end` (`floor(now/60)=floor(end/60)`). Цена,
согласно общему legacy исполнителю, задаётся close сигнальной H4 свечи, а
`fill_t` — фактическое время наблюдения `now`; текущие или будущие high/low M1
не участвуют в выборе цены входа. Если минуту границы пропустили, бар разрешено
учесть для контекста, но сигнал по нему не исполняется задним числом. Цена входа
получает существующую неблагоприятную `cost` на входе. Стоп покупки — минимум
low последних 10 закрытых H4 свечей,
включая сигнальную, минус 0.1 ATR; для продажи зеркально максимум high плюс
0.1 ATR. ATR — простое среднее `high-low` последних 14 закрытых H4 свечей,
включая сигнальную; без полного периода или при невалидном расстоянии до стопа
сделки нет. Цель — 2R, где R — расстояние фактического входа до исходного
стопа. Сопровождение и закрытие используют общий lifecycle swing.

Параметры fast EMA в JSON ограничены значениями 8, 12, 16, 20 баров; slow
EMA — 32, 40, 50 баров; допустимы только `fast < slow`. Общие JSON-поля
`atr_period`, `stop_lookback_h4_bars`, `stop_buffer_atr`, `rr_fixed` и
`take_profit` для этой семьи должны соответственно задавать 14, 10, 0.1 и 2,
`fixed`. Код не подставляет эти значения вместо отсутствующих параметров.
Это заранее ограниченное пространство первого исследования, а не гарантия
результата.

Для сравнения baseline и нового семейства используется одинаковый legacy
lifecycle, одинаковая единица R и те же цены/издержки. `cost` применяется
неблагоприятно один раз при входе, как в существующем `Swing::minute`; варианты
×1/×2/×3 умножают его одинаково для baseline и кандидата. Стоп и цель
проверяются по наблюдаемым M1 high/low; если оба достижимы в одной минуте,
первым считается stop. Stop исполняется на заданном стоп-уровне даже при гэпе
через него: модель не имеет M1 open в общем API и не оценивает дополнительное
проскальзывание гэпа. Target исполняется на целевом уровне. Это явное
ограничение исторической модели; изменение его требует отдельной общей модели
исполнения и повторного baseline.

После смены семейства опубликованные Pending/Active сделки продолжают
сопровождаться на исходных уровнях, с исходной конфигурацией исполнения и без
повторной публикации. Новое семейство начинает создавать сигналы по новой
конфигурации; старые снимки без поля семейства читаются как legacy swing.

Stable ID сигнала остаётся зарегистрированным после Stop, Target, Cancelled или
другого терминального события. Прогрев после рестарта или смены конфигурации не
переиздаёт и не возвращает под сопровождение уже зарегистрированный ID.
Регистрация учитывает как подтверждённые Telegram-сообщения, так и исходящие
сообщения в очереди доставки; чтение очереди не меняет её статус, порядок или
содержимое. Это правило распространяется и на терминальное сообщение, которое
ещё не было доставлено.

### Проект общего бюджета входов портфеля — V4-D4

Это проект следующего исследования, а не реализованное требование. Проверяется
фиксированный кандидат раунда 007: EURUSD qmc-027, GBPUSD qmc-086 и USDJPY
`rr_fixed=2`, `take_profit=target`. Параметры не меняются; каждая допущенная
сделка сохраняет риск 1R. Baseline остаётся исходным и не получает новый лимит.
Предлагаемое поле wrapper-файла — `portfolio_admission.max_open_positions=3`.
Отсутствие `portfolio_admission` означает прежнее неограниченное поведение;
заданный лимит должен быть положительным целым. Локальный
`trend_pullback.max_open_positions` остаётся отдельным ограничением только для
новых TP-входов. В общий бюджет входят Pending и Active выбранных пар, включая
retired-конфигурации; сигналы основного движка, не опубликованные как сделки
кандидата, не занимают его слоты.

Pending занимает один reservation slot с момента admission. Pending → Active
переводит тот же слот, не создавая второй. Stop, target или cancel создаёт
terminal reserve до `max(terminal_observed_minute, observed_watermark_minute)`
включительно; слот повторно доступен только в более поздней UTC-минуте. Уже
созданные заявки и позиции при включении/снижении cap не отменяются и не
закрываются; если занято больше нового лимита, новые intents пропускаются без
очереди до освобождения. Общий cap, его занятость и terminal reserves не меняют
1R на сделку.

Один coordinator используется живым Runtime и совместным replay; независимые
CSV с последующей фильтрацией не подходят. Он получает typed `EntryIntent`,
сохраняет общий admission state и пропускает принятую сделку через существующий
Swing executor. Внешний опубликованный signal ID остаётся совместимым и не
используется для упорядочения. Внутренний `intent_key` — стабильный упорядоченный
кортеж `(config_generation:u64, family_code:u8, plan_id:UTF-8 bytes,
source_event_ms:i64, direction_code:u8, intent_ordinal:u64)` внутри символа.
Сравнение чисел числовое, строк — лексикографическое по байтам; enum-коды
закрепляются версией схемы. Общий порядок intent: фактический UTC event time,
ASCII bytes символа, затем этот кортеж. `event_time_utc` означает
`observed_at_utc` — фактическую доступность события coordinator, не source quote
time, `signal_t` или `fill_t`. `intent_ordinal` монотонен в пределах
поколения конфигурации/символа/семейства/плана, различает correction attempts с
одинаковыми внешними ID и source event и сохраняется в snapshot. Перебор
hash-map не может определять результат.

Причинные часы ведутся отдельно от совместимых CSV полей. В event ledger
сохраняются source quote UTC time и фактическое UTC time доступности события,
`admitted_at_utc`, `executed_at_utc` и `exited_at_utc`; также сохраняются прежние
`signal_t`/`fill_t`, quote/batch IDs, решение, reservation occupancy и initial
risk. Для legacy `signal_t=bar.end`; старый рыночный `fill_t=bar.end` может
оставаться в raw CSV ради совместимости, но не переносит фактическое исполнение
или риск назад по времени. Admission происходит при фактическом решении координатора. `observed_at_utc_ms`
в live задаётся инжектируемыми системными UTC wall clock часами сразу после
получения полного ответа `markets()`; все quotes batch получают этот сохранённый
момент получения, а не время source quote. Batch ID и момент сохраняются в
durable inbox до обработки; retry и повтор commit используют прежние значения,
не читают часы заново. Все значения — Unix milliseconds UTC. В историческом
joint replay полная M1 строка с интервалом `[start_utc_ms, end_utc_ms)` становится
доступной на исключительной правой границе `end_utc_ms`. Admission, fill и exit,
полученные из этой строки, получают это причинное время, даже если legacy
`signal_t` или raw `fill_t` указывают на более ранний момент. Replay сохраняет
исходный интервал строки и совместимые timestamp отдельно. Цены и порядок
исполнения остаются как в V3: market entry использует предусмотренную движком
цену с неблагоприятным cost; проверка stop выполняется перед target по полному
M1 high/low; уровни fill не меняются. OHLC не даёт времени точного внутриминутного
касания, поэтому ledger отражает момент доступности полной строки, а не
восстанавливает такой момент. В live fill/exit используют captured
`observed_at_utc_ms` события.

Когорта сделки определяется фактическим `executed_at_utc`; admission, fill и
exit сравниваются с границами окна по их UTC времени. Для `[start, cutoff)`
обрабатываются только события, доступные строго до cutoff. Admission/fill/exit
ровно на cutoff не входит в интервал. Сделка, исполненная до cutoff и всё ещё
открытая, оценивается по последней наблюдаемой цене строго до cutoff; будущие
выходы цензурируются. Это применяется одинаково к baseline и кандидату. Raw
baseline CSV побайтно сохраняется отдельно; совпадение его байтов и корректность
новых сравнительных метрик являются разными проверками. Если причинный ledger
меняет прежние baseline метрики, baseline пересчитывается тем же методом, а
разница документируется.

NS-05 peak open initial risk — сумма исходного риска только исполненных Active
сделок от `executed_at_utc` до `exited_at_utc`, с консервативным порядком входов
перед выходами при совпадающем времени. Pending не несёт открытого риска; при
Pending → Active reservation остаётся одним слотом, а initial risk учитывается
один раз. Pending + Active + terminal reserves — отдельная метрика занятых
слотов и диагностический инвариант соблюдения cap. Она не подменяет gate
пикового открытого риска. Оба показателя сохраняются для каждой стороны
сравнения; NS-05 не меняется.

Live coordinator получает один `MarketBatch` на один полностью полученный
ответ `markets()`. Все quotes в ответе получают один captured
`observed_at_utc_ms`, поэтому это одна observed-minute группа, даже если source
quote timestamps пересекают минутную границу. Batch атомарен: occupancy;
admission всех intents в порядке `(observed_at_utc, ASCII symbol, intent_key)`;
затем исполнение Pending и exits. Exit в этом ответе не освобождает slot для
другого входа того же ответа. Для source-late классификации берётся
`source_watermark_utc` до начала batch; соседний инструмент не меняет статус
котировки порядком обработки. После обработки watermark становится максимумом
допустимых source timestamps.

В joint replay каждая полная M1 строка доступна на `end_utc_ms`; replay обрабатывает
causal-minute группы по наблюдаемому времени. Для каждой группы повторяются
фазы occupancy, admission, execution/exit, затем продвигается
`observed_watermark_utc`. Это даёт пример: A закрывается в 10:00, B с событием
доступности 10:00 отклонён, C с доступностью 10:01 допущен. Пример относится к
разным causal times replay, не к одному live response. Не обещается равенство
при разбиении live ответа, если оно меняет captured observed time. Повторный
запуск воспроизводим при тех же сохранённых событиях, captured times и порядке.
Весь batch транзакционен; ошибка commit не расходует slot и не оставляет
частично применённую последовательность.

Сохраняются два разных watermark. `source_watermark_utc` — максимум уже
обработанных допустимых source timestamps; он используется только для
межпарного late-классификатора. `observed_watermark_utc` — максимум причинных
времён обработанных событий; его UTC-минуты определяют terminal reserves и
освобождение slots. Source time никогда не сравнивается с observed watermark.
Оба значения сохраняются; повтор batch использует сохранённый captured
`observed_at_utc_ms`.

Source-late quote с `source_timestamp < source_watermark_utc`
классифицируется относительно значения до обработки batch. При включённом общем
cap она не создаёт новый admission; без `portfolio_admission` late-статус только
диагностический и не блокирует прежний локально допустимый entry. В обоих режимах
локально допустимая quote без дубля сопровождает существующие Pending/Active,
включая retired; сохраняются per-pair дедупликация, порядок котировок и
per-symbol TP cap. Fill/exit по ней получает captured `observed_at_utc_ms`, без
пересчёта прошлого; слот освобождается не раньше следующей observed UTC минуты.
После batch source watermark становится максимумом допустимых source timestamps.

Старый snapshot восстанавливает source watermark из сохранённых source
timestamps. Если observed watermark отсутствует, нельзя использовать `Tick.millis`
как время получения. При первом обрабатываемом batch его captured
`observed_at_utc_ms` один раз сохраняется как `bootstrap_observed_at_utc_ms`;
для старого inbox без этого поля берётся фактический момент начала первой
обработки. Retry использует сохранённое значение. Occupancy восстанавливается
из current/retired Pending+Active без изменения условий сделок. При включённом
общем cap admission блокируется всю первую observed-minute bootstrap, но
сопровождение, исполнение существующих Pending и выходы работают сразу.
Admission возобновляется строго со следующей observed-minute при свободном
бюджете. Bootstrap time и barrier сохраняются в snapshot, restart не сбрасывает
и не продлевает их. Без общего cap bootstrap barrier не блокирует admission.
Ordinary delivery latency не классифицируется через сравнение source и observed
clocks. Локально обратное/дублирующееся событие отклоняется прежней защитой пары;
quote dedup включает pair/source/source timestamp/price, batch ID защищает от
повторной транзакции.

Append-only ledger для обеих сторон сравнения содержит `intent_key`, прежний
внешний ID, source quote time, `observed_at_utc`, `admitted_at_utc`,
`executed_at_utc`, `exited_at_utc`, batch/quote IDs, решение, occupancy до/после,
terminal reserve и исполненный initial risk. Peak open initial risk вычисляется
только по интервалам Active-сделок с консервативным entry-before-exit порядком.
Reservation слоты считаются отдельным потоком Pending/Active/terminal barriers;
uncapped baseline CSV сохраняет прежние поля. Сравнительные метрики baseline и
кандидата проходят через один event-time replay/accounting helper.

При полном лимите попытка legacy-входа пропускается без скрытой очереди:
исходный план остаётся `WaitEntry`, срок и цель не меняются, обработанный H4
trigger отмечается, чтобы повтор этого бара не создавал новый intent. Поздний
новый H4 бар может создать попытку лишь если сам выполняет исходное правило.
Индикаторы и контекст продолжают обновляться. Отказ Range не создаёт Trade или
`Sweep`, не увеличивает stop counter и не проверяет противоположную сторону на
той же свече; новую попытку может создать только отдельное следующее торговое
событие.

Граница смены конфигурации — `switch_at_utc_ms`, UTC миллисекунда успешного
атомарного commit проверенной конфигурации и нового `config_generation`; оба
значения сохраняются в snapshot. Для новой конфигурации любой бар с
`bar.end_utc <= switch_at_utc` является только контекстом, даже если закрытие
впервые обнаружено следующей котировкой. Новое admission возможно лишь для бара
с `bar.end_utc > switch_at_utc`, после фактического наблюдения с
`observed_at_utc > switch_at_utc`. Равенство границе относится к старому
поколению. Retired Pending/Active продолжают сопровождаться на исходных уровнях
независимо от границы и занимают общий slot. Все новые конфиги валидируются до
переключения; switch time, generation, Swing state, coordinator state и outbox
фиксируются атомарно.

При холодном старте три выбранных минутных потока совместно прогреваются по UTC
через тот же coordinator; нельзя прогреть пары независимо и затем отфильтровать
сделки. При старом snapshot occupancy восстанавливается из current/retired
Pending+Active без изменения торговых условий. Source watermark берётся из
сохранённых source timestamps. Если observed watermark отсутствует, он один раз
инициализируется captured временем первого batch; для старого inbox без времени
— фактическим началом его первой обработки. При включённом cap на всю эту
observed-minute действует admission barrier, но исполнение Pending,
сопровождение и выходы существующих сделок доступны сразу. Admission снова
разрешается только со строго следующей observed-minute при свободном бюджете.
Bootstrap time и barrier переживают restart. Без общего cap barrier не блокирует
локальные admission. Старые позиции продолжают исполняться независимо от смены
профиля.

До реализации обязательны Docker RED-сценарии: M1 open выше target при low,
достигшем stop, сохраняет Stop V3 stop-first по high/low; полная строка на cutoff
исключена; V3 market price/adverse cost/fill levels и raw CSV parity отдельно от
causal accounting. Pending не добавляет open risk, Pending→Active учитывает его
один раз. Один live response с source timestamps по разные стороны минуты имеет
единое observed time и admission-before-execution; source-late классифицируется
по предbatch source watermark; обычная задержка не смешивает часы. Locally valid
source-late quote сопровождает существующие current/retired сделки на captured
observed time, не создаёт admission при cap, следующий rebound не отменяет stop;
проверить capped/uncapped, restart и release только после следующей
observed-minute. Replay 10:00/10:01 проверяет A-close/B-rejected/C-admitted.
Также: correction IDs до/после restart, switch с gap/late H4 и strict UTC boundary;
настоящий старый snapshot без обоих watermark с повторным restart и сохранённым
bootstrap barrier; один и тот же locally valid source-late H4 intent разрешён
uncapped и блокируется capped, при одинаковом сопровождении существующих позиций.
NS-05 gates без изменений.

### Правила «свинг» в работе бота

| Тема | Правило |
|---|---|
| Включение и отключение | Файл правил «свинг» — `strategy/swing-rules.json`, путь задаёт настройка `SWING_STRATEGY`: `{"comment": ..., "comments": {"<параметр>": "<пояснение>"}, "instruments": {"<SYMBOL>": {параметры}}}`. Каждый параметр инструмента указывается явно, значений по умолчанию нет: пропущенный или неизвестный параметр отклоняется. Для каждого параметра в `comments` есть пояснение (вложенные — через точку, например `range.wick_min`); `comment` и `comments` — пояснения, не условия расчёта. Инструменты — только из основного JSON. Без настройки или при исключении инструмента прекращается создание новых swing-планов и заявок; по инструменту снова публикуются сигналы основного движка. Уже опубликованные swing-заявки и сделки остаются в снимке и сопровождаются по сохранённым параметрам и уровням до обычного исполнения, отмены или закрытия. Их waiting-планы не создают новых заявок. |
| Что публикуется | Для инструментов из файла в чат идут сделки правил «свинг»; сигналы основного движка по этим инструментам в чат не отправляются, сам движок продолжает считаться. |
| Сообщения | Новая сделка по рынку, новая лимитная заявка, исполнение заявки, стоп, тейк, снятие заявки, выход по индексу доллара. Если первая котировка после закрытия свечи создаёт лимитную заявку и исполняет её, публикуются лимитная заявка и исполнение именно в таком порядке, даже если после исполнения сделка остаётся Active. Если та же котировка также достигает стопа/тейка, после них публикуется выход. Тип входа определяется тем, что заявка была лимитной, а не сравнением времён сигнала и исполнения. Сообщение о лимитной заявке показывает исходный лимитный уровень и RR до издержек входа; сообщение об исполнении показывает фактическую цену входа с издержками и соответствующий RR. Это различие сохраняется, когда оба сообщения создаются после одной котировки. Повтор и восстановление не дублируют события. Время в сообщении — фактический UTC timestamp обрабатываемой котировки в RFC3339; время сетки источника используется только для расчёта правил. В тексте: пара, направление, вид (тренд, коррекция, боковик), вход, стоп, тейк, RR и событие. Идентификатор сделки для ответов в чате — `<SYMBOL>:swing:<вид>:<направление>:<время сигнала>`. |
| Прогрев | При первом запуске с файлом и после изменения параметров инструмента правила прогоняются по всем минутам инструмента в базе. Сделки, закрытые при прогреве, не публикуются; оставшиеся открытыми и лимитные заявки публикуются один раз с пометкой «до запуска». |
| Котировки | Каждая котировка — минута с одинаковыми максимумом и минимумом; свечи — от агрегатора бота, включая неполные. |
| Сохранение | Состояние правил хранится в снимке бота и после перезапуска продолжается без повторных сообщений. Хранятся только данные, от которых зависят дальнейшие решения: последние 128 свечей D и H4, живые зоны, фракталы, нужные для целей, структуры и стопов, и последние 100 событий. |
| Выход по индексу доллара | В живой работе не подключён: нужны котировки шести пар. Параметр `reference_exit` в файле отклоняется. |

### Пересчёт ожидающих условий основного движка

После изменения торговых правил пересчитываются только планы `wait_confirm` и
`wait_entry`; сохраняются их ID и срок жизни. Для каждого такого плана в чат
передаются ID операции изменения, ID плана, направление и действующие после
пересчёта условия, включая применимые параметры подтверждения или входную зону.
Повторная доставка и восстановление после перезапуска не создают повторных
сообщений даже при повторном переходе между прежними версиями правил.
Опубликованные `setup`/`active` и завершённые результаты сохраняют уровни.
Изменение только комментария планов не пересчитывает.

## Работа с данными

Достаточность свечей проверяется по JSON. Недостаток данных для нового сигнала
не отменяет сопровождение уже выданного по наблюдаемым котировкам. Стык источников
и недостающий период требуют проверки; равенство цен архивного источника, Upscale и ICE
в TradingView не установлено. Статус импорта и подключения находится в плане.

## Хранение правил и настройка

Рабочий JSON — единственный источник правил, в SQLite нет их копий или наборов
правок для восстановления файла. При запуске файл читается и проверяется;
ошибка не заменяется сохранённой конфигурацией. Telegram-правки сначала атомарно
сохраняются в JSON, затем применяются. Список инструментов применяется после
перезапуска. Состояние и контроль доступности котировок отдельны для каждой пары.

Поддерживаемые параметры и политики изменяются через JSON. Текстовые определения
не являются исполняемой программой: новый алгоритм может потребовать изменения
Rust-кода. Неподдерживаемое изменение должно быть явно отклонено с пояснением,
а не незаметно заменено другим правилом.

Поддерживаемая SQLite v4 изменяется с сохранением данных и привязок сигналов;
старые схемы SQLite отклоняются без миграции. Миграция версии календаря в снимке
поддерживаемой схемы сохраняет опубликованные сигналы и пересчитывает контекст.
Токены Telegram/OpenAI, модель, группа и параметры запуска хранятся отдельно
от стратегии. Все участники настроенной группы имеют одинаковые права на правки.

## Служебные сообщения и границы продукта

После успешного запуска демона в группу отправляется «Бот запущен» с временем UTC.
Это служебное сообщение; ответ на него не запускает изменение стратегии.

В stdout/journald каждые 5 минут выводятся «Работаю», время последней принятой
котировки UTC или «нет», число ожидающих планов. После обработки полной закрытой
H4 выводится результат поиска сигнала и краткая причина его отсутствия.
Эти логи не отправляются в Telegram.

Бот устанавливается пользователем вручную на Linux x86_64 под systemd.
SSH и автоматическая установка не входят в работу приложения. Пауза/откат по
команде, голосовые сообщения, отдельный внешний мониторинг, напоминания о ключах,
бюджетный контроллер, суточные сводки и подбор параметров не входят в согласованный объём.

## Локальный бэктест

`forex-backtest` запускается только локально через Docker: --strategy, обязательные
--from/--to (UTC, [from,to)), необязательные --symbols (иначе все из JSON), --output.
--data-config задаёт пути архивных котировок отдельно от стратегии. Каталог результата новый.
Ключи, сеть и серверная БД не требуются; серверный JSON автоматически не синхронизируется.
До начала загружаются закрытые свечи и наблюдаемая часть текущих свечей; позиции
и планы начинают пустыми. minimum_bars обязателен, нехватка bars_analyzed раскрывается.
Результат по наблюдаемым индексным котировкам: рынок по цене индекса,
лимит и тейк по уровню без улучшения, стоп по первой наблюдаемой цене индекса.
R фиксируется расстоянием вход–стоп. Издержки не моделируются.
Известные исключённые интервалы помечают затронутые сделки; сценарные диапазоны не строятся.
Открытые сделки в конце показываются отдельно с текущим R и временем цены.
PDF на русском: сводка, кривая закрытого R/просадка, пары/месяцы, качество,
открытые/отменённые сигналы, 3 лучших/3 худших/3 случайных примера без повторов.
Сохраняются JSON правил и результатов, журнал JSONL, CSV сделок, графические данные,
хеши источников и версия. PDF пересобирается без прогона. Подбор параметров и
сравнение запусков не входят. Источники и рабочие базы не изменяются.

Оформление отчёта за октябрь 2026 года одобрено пользователем 10.11.2026

Сводка предшествует деталям и качеству данных; каждый пример сделки начинается

## Контракт стратегии v2

Файл является строгим JSON с явными числами и типизированными политиками.
Поля comment поясняют настройки, но не влияют на расчёты. OpenAI получает их
и может редактировать по просьбе пользователя; неподдерживаемые условия нельзя
реализовать одной правкой пояснения. Изменение только comment/messages не
пересчитывает планы. Формат v1 больше не читается, конвертера нет.

Пять ранее текстовых окон заданы положительными целыми параметрами в барах:
запасной H4-стоп, возраст встречной зоны подтверждения H4, окно недельного
снятия и отдельные D/W-окна фрактальных целей. Смысл и единицы всех полей,
соответствие v1/v2 и ограничения описаны в [архитектуре](architecture.md).
Нереализованные weak_bars и отметка дневного снятия за 30 баров удалены;
отключённые модули остаются явно отключёнными, новая торговая логика не добавлена.

Пользователь самостоятельно выбирает поставщика истории. Импорт и бэктест
не проверяют название конкретного поставщика, но требуют совместимый формат
и явно указанное происхождение. Автоматическая загрузка истории конкретного
поставщика не входит в подготовку набора; данные готовятся пользователем.

## Котировки Upscale и индексные сигналы

По согласованию от 12.11.2026 текущий источник — Upscale, демо-счёт.
run требует UPSCALE_API_KEY и ровно один активный API-enabled demo account.
Все инструменты JSON запрашиваются одним GET каждые 2 секунды после завершения
предыдущего запроса. Никакие ордера не отправляются.

Сопоставление: EURUSD → EUR/USD, GBPUSD → GBP/USD, USDJPY → USDJPY/USD.
Проверяются ticker/baseAsset/quoteAsset, уникальность рынка, цена, время и
флаги рынка. Неизвестные, неоднозначные, некорректные и устаревшие открытые
рынки отклоняются. Ошибка одной пары не блокирует остальные.

Расписание `schedule` читается из того же ответа для каждой пары. При
`inPause=true` индекс не передаётся в расчёт; после окончания перерыва
передаются только свежие котировки, прошедшие прежние проверки. `schedule=null`
означает круглосуточный рынок. Опрос продолжается с прежним интервалом, без
отдельных запросов расписания. Начало и конец планового перерыва не вызывают
сообщений в чат или уведомлений о потере/восстановлении котировок.

probe-upscale <env-file> однократно читает все активные демо-счета и их рынки,
без Telegram/OpenAI/SQLite. Нет подходящего счёта — ошибка. Вывод содержит
индексные цены fp9, UTC-время в миллисекундах и статусы, без ключа и персональных
данных. Ключ необязателен для офлайн-команд; указанные пустые значения,
дубликаты и неизвестные имена env отклоняются.

## Торговые методы адаптера Upscale

Отдельные методы адаптера Upscale позволяют открыть позицию по рынку,
прочитать открытые позиции счёта и закрыть заданный объём позиции по рынку.
Параметры передаёт вызывающий код: счёт, рынок, направление, сумма резерва и
плечо для открытия; идентификатор позиции и объём базового актива для закрытия.
Все суммы, объёмы и плечо — строки fp9 без преобразования через float.
Методы возвращают статус ордера и ошибку исполнения, не приравнивая принятие
ордера к исполнению. Ключ идемпотентности задаётся вызывающим кодом;
автоматических повторов торговых запросов нет.
Эти методы не подключены к сигналам или CLI. Работающий бот по-прежнему
не отправляет ордера; стратегия, БД и уведомления не меняются.

## Единая индексная цена

Единственная цена свечей, входа, стопа, цели и отмены — индекс Upscale.
Котировка содержит symbol, millis (UTC, миллисекунды), price (целое в масштабе
1 000 000) и source. Цена положительна. Старый двухценовой формат не поддерживается.
Политики выбора стороны цены удаляются из JSON; candles.price_basis=index.
Рыночный вход и стоп используют наблюдаемую цену; лимит и тейк — заданный уровень.
Комиссии, своп и дополнительные издержки не моделируются.

База создаётся с нуля по DATABASE_PATH=data/signals.sqlite. Старые файлы БД и
архивы не изменяются и не подключаются; преобразование старых данных не выполняется.
Бот восстанавливает только своё новое состояние; автоматического прогрева из архива нет.
Индексный бэктест использует общий обработчик котировок и требует достаточной
истории индекса. Отсутствующие интервалы не заполняются, происхождение сохраняется.
Формат истории описан в [history-data.md](../history-data.md).
Загрузка истории Upscale не реализуется в этой задаче.
