# Архитектура

Поведение продукта задают [требования](requirements.md), торговые правила —
локальный `strategy/fvg-bot-rules.json`. [План](development-plan.md)
отделяет выполненное и проверенное от оставшихся работ. Ниже описано целевое
устройство по текущему JSON, а не утверждение о готовности всех частей кода.

## Поток обработки

Предыдущие свечи и текущие котировки → расчёт по каждой паре → планы и сигналы → Telegram.
Ответ на сигнал текстом или скриншотом → сохранение → OpenAI → проверка и запись JSON
→ пересчёт ожидающих планов → пояснение в Telegram.

Серверный бот — один Rust-процесс. Координатор последовательно меняет состояние;
рабочие потоки получают котировки, Telegram updates, ответы OpenAI и доставляют
сообщения. Медленный HTTP-запрос не останавливает обработку котировок.
OpenAI используется для комментариев, а не для расчёта каждого сигнала.

Разработка, тесты и сборка выполняются в Docker; на Ubuntu 26.04.1 LTS запускается
готовый Linux x86_64-бинарник под systemd. Версии заданы в Dockerfile и Cargo.lock;
зависимости — в bot/Cargo.toml. SQLite хранит состояние, Telegram работает через long polling.

## Загрузка стратегии

При запуске читается локальный рабочий JSON, исключённый из Git.
`example.json`, встроенные параметры и содержимое SQLite не подменяют файл.
Тесты читают рабочий JSON; после клонирования, перед запуском тестов и приложения,
он создаётся вручную из `example.json` по инструкции README. Контракт проверяет обязательные
и неизвестные поля, типы, повторные ключи, ID правил, диапазоны, перечисления и ссылки.
Числа должны быть конечными; объём свечей — не меньше минимума, RR — положительным
и согласованным с потолками. Инструменты уникальны, шаг цены положительный.

Условия JSON сопоставлены типизированным блокам Rust по ID, а не позиции в массиве.
Текст формул и определений не исполняется как код. Параметры читаются из JSON;
неподдерживаемая политика отклоняется явно. Ограничения текущей реализации
перечислены в плане и не меняют смысл стратегии.

| Разделы JSON | Ответственность |
|---|---|
| `instruments`, `candles`, `context`, `policies.trade_window` | Инструменты, свечи, достаточность данных, доступное время торговли |
| `policies.zones`, `policies.fractals`, `parameters` | ATR, зоны, фракталы, направление и параметры расчёта |
| `policies.plans` | Планы W/D/H4, подтверждение, вход, сроки, сопровождение |
| `policies.targets`, `policies.execution` | Цели, цена входа, единая индексная цена, отмены |
| `policies.positions` | Независимость планов, защита от дублей, применение новых правил |
| `policies.modules` | Признак отключённого модуля боковиков |

`check-config [путь]` проверяет файл без сети и изменений: код 0 — успех,
1 — ошибка чтения/конфигурации, 2 — аргументы. Без пути используется
`strategy/fvg-bot-rules.json` относительно текущего каталога.
`describe-config [путь]` выводит JSON Pointer полей, значения без пояснений,
ограничения параметров, допустимые политики, пути comment и разрешение Telegram-правок.
Карта не подтверждает выполнение торговых правил; готовность определяется тестами
и приёмкой в плане. Диагностика не печатает значения ошибочных полей и секреты.

## Данные каждой пары

Координатор хранит отдельные движок, агрегатор и признак доступности потока для
каждого символа из `instruments`. Свечи, планы, сигналы и события имеют символ
в ключе; шаг цены берётся из `instruments[].price_tick`, масштаб —
`instrument_price_tick_scale`. Единица цены — валюта котировки за единицу базовой
валюты, а не USD за EUR для всех инструментов. Цены представлены целыми числами;
округление входа не должно ухудшать требуемый RR, отступ стопа округляется наружу.

Upscale предоставляет GET `/v2/markets?accountId=...`. Опрос раз в 2 секунды
возвращает снимки всех инструментов. Проверяются символ, источник,
положительный indexPrice и UTC timestamp. Повтор одинакового события не создаёт
повторного действия, обратное время отклоняется. Источники не склеиваются незаметно;
пропуски не заполняются. REST при закрытом рынке не доказывает работу живого потока.

## Свечи и расчёт текущей ситуации

Для импортированных минут и потока используется одна сетка из `candles`:
America/New_York с DST, D1 в 17:00, неделя с воскресенья 17:00, H4 в 01/05/09/13/17/21.
При повторяющемся осеннем 01:00 границей служит первое вхождение; длина
интервала в UTC меняется вместе с DST. RR поддерживает до девяти десятичных
знаков и значения до 1000000; расчёт использует целочисленные дроби без усечения.

Время хранится в UTC. Интервалы полуоткрытые: котировка на границе относится
к следующей свече. На общей границе обработка идёт W → D → H4.

Из предыдущих закрытых свечей рассчитываются зоны, фракталы и направление.
Количество и минимумы задаёт `context`. Эта загрузка не создаёт прошлые планы и сигналы. В коде операция называется `seed`;
это внутренняя часть загрузки данных, отдельного режима продукта нет.
Повтор одинакового закрытого бара не меняет результат; другая версия уже
обработанного бара и обратное время отклоняются.

Агрегатор сохраняет незакрытые бары выбранной основы цены и последнюю котировку. Пустые интервалы
не создаются. Первый неполный бар, бары после разрыва потока и незакрытые бары
после перезапуска не выдаются за полностью наблюдавшиеся. Новые сигналы требуют
свежих котировок и достаточных данных; сопровождение выданных сигналов продолжается
по наблюдаемым ценам. Движение цены за пропуск не восстанавливается предположением.

## Расчёты и состояния

ATR, образование FVG/гэпов, реакции, инверсии, фракталы и направление вычисляются
по `policies.zones` и `policies.fractals`. ATR зоны выбирается через
`parameters.atr_reference_zone`, стопа — `policies.atr.stop_reference`. Гэп отличается способом образования и далее проходит
те же правила зоны. Происхождение зоны сохраняется для объяснения сигнала.

План хранит инструмент, ID правила, время, направление, POI и её таймфрейм.
Состояния определены типами движка: `wait_confirm`, `wait_entry`, `setup`, `active`, `done`.
У четырёх дневных правил correction/continuation POI дневная; у `W_point_A` недельная.
Повтор правила для той же ситуации не создаёт дубля, независимые планы не теряются.
Смена недельного направления обрабатывает каждый план согласно `policies.plans.weekly_rules`;
активный сигнал продолжает сопровождаться отдельно до результата.

Подтверждение и вход проверяются по `policies.plans` и `parameters`. Возраст зон, включение IFVG,
допустимый диапазон лимитной цены и сроки ожидания берутся из JSON. Отключённые
модули не участвуют в расчёте. Точные условия не дублируются вторым алгоритмом
в документации. Структурная цель и ограниченный потолком тейк сохраняются отдельно.

После закрытия подтверждающей H4 используется первая доступная котировка.
Отмена ожидающего входа проверяется до исполнения: стоп/цель по индексной цене,
условие пробоя инвертированной зоны — по закрытию H4 и запасу из JSON.
Закрытые бары и истечение срока обрабатываются до входа по котировке.
Отмена терминальна; последующее касание входа не активирует отменённый сигнал.
Стоп/тейк отслеживаются по котировкам, без ожидания следующей H4 и без
предполагаемого порядка движения внутри свечи.

## Сохранение и восстановление

SQLite содержит котировки, отчёты импорта, состояние расчёта, планы, сигналы,
результаты, комментарии, авторов, привязки сообщений и задания. Конфигурация
хранится только в JSON; снимок содержит хеш правил и состояния по символам.
Изображения сохраняются рядом с БД в `attachments` с идентификацией по SHA-256.

В одной транзакции сохраняются входное событие, изменения состояния и очередь
исходящих сообщений (outbox). Только после успешной записи меняется состояние
в памяти. Повтор ID и содержимого события не применяет его заново; конфликт
содержимого отклоняется. Подтверждение доставки и привязка Telegram-сообщения
к сигналу также сохраняются атомарно. Недоставленные сообщения остаются после сбоя.
Потерянный ответ Telegram может дать дубль доставки; exactly-once не обещается.

SQLite открывается только при поддерживаемой схеме v4; старые схемы и чужие БД
отклоняются и не мигрируются. Внутри v4 поле версии календаря снимка может вызвать
переход расчётного контекста на текущую сетку: опубликованные сигналы, уровни,
результаты, комментарии и привязки сохраняются, а контекст восстанавливается из
сохранённых минут. Это миграция снимка приложения, а не миграция старой схемы БД;
исторические результаты и исходные данные не переписываются. Повтор после сбоя
безопасен. Устаревшие задания изменения опубликованных уровней не доставляются.

## Комментарии и изменение JSON

Telegram принимает ответы из настроенной группы на известный сигнал или уточнение.
Сохраняются update_id, message_id, chat_id, author_id, текст/подпись и изображения.
Все участники равноправны. Offset увеличивается после устойчивого сохранения update.
Фото выбирается в максимальном разрешении; изображение-файл проверяется по MIME
и сигнатуре PNG/JPEG/WebP/GIF. Ошибка загрузки не заменяется пустым изображением.

FIFO-очередь обрабатывает каждый ответ как новое дополнение на актуальных правилах.
OpenAI Responses API получает модель из сервисных настроек, `store=false`, лимит
ответа, нужные правила, связанный сигнал, текущий комментарий и изображения.
Для уточнения добавляется относящаяся к нему ветка, а не весь чат. Ответ имеет
строгую схему `apply/clarify/no_change`, пояснение и изменения действующих скалярных параметров и строковых comment
по разрешённым JSON Pointer из каталога контракта. Новые алгоритмы и произвольные пути не применяются.
Неоднозначный комментарий вызывает уточнение без изменения правил.

Кандидат проверяется целиком. Сохраняются ID операции и хеши полного документа до/после без копии
правил; расчётный хеш исключает comment и messages; файл записывается через временный файл и атомарный rename, затем фиксируются
состояние и сообщения. После сбоя операция сверяется с JSON и завершается без
повторного применения правки. Ошибка записи не меняет правила в памяти.

После изменения пересчитываются `wait_confirm`/`wait_entry` с сохранением их
идентичности и времени жизни. Для каждого плана сообщение содержит ID операции,
symbol и ID плана в ключе идемпотентности, поэтому повторный цикл между уже
встречавшимися версиями правил не конфликтует с прежней доставкой. Текст сообщает
направление и фактические действующие условия после пересчёта: для wait_confirm —
параметры и правило подтверждения, для wait_entry — текущую входную зону и
применимые условия входа. `setup`/`active` сохраняют вход, стоп, структурную
цель и тейк согласно `position_rules.rule_update`; завершённые результаты неизменны.
В чат отправляются пояснение изменения и новые условия ожидающих планов.
Доставка пояснения не переключает уровни опубликованного сигнала.

Для swing, если первый тик после закрытия свечи создаёт и исполняет лимитную
заявку, outbox содержит лимитную заявку и исполнение в причинном порядке,
даже если сделка остаётся Active. Если этот же тик достигает стопа/тейка,
следом публикуется выход. В тексте лимитного события используются первоначальный
уровень заявки и RR до издержек; событие исполнения показывает цену с издержками
и RR по фактической цене исполнения, даже если оба события сформированы после
того же тика. Состояние заявки сохраняет тип limit независимо от
совпадения timestamp сигнала и исполнения; повтор тика и восстановление снимка
идемпотентны.

## Сбои и внешние вызовы

| Сбой | Действие |
|---|---|
| Нет котировок | Уведомить группу, приостановить новые сигналы; не приписывать результаты пропущенному периоду. |
| Нет OpenAI | Уведомить, продолжать сигналы по JSON, сохранять комментарии и автоматически продолжить очередь после восстановления. |
| Нет Telegram | Сохранить исходящие сообщения до восстановления. |
| Ошибка записи состояния | Завершить процесс; systemd перезапустит его с сохранённым состоянием. |
| Невалидная правка | Сохранить действующий JSON, дать пояснение, не повторять платный запрос бесконечно. |

Сетевые запросы имеют connect/request timeout, предел размера ответа и ограниченные
повторы с задержкой. Ошибки доступа, временные сбои и невалидные ответы различаются;
уведомление создаётся один раз на инцидент. HTTP-транспорт подменяется в тестах.
Токены, Authorization, тела ответов и URL Telegram с токеном не попадают в диагностику.
API-модель не получает доступ к SSH или shell. Расход токенов сохраняется при наличии usage.
Большие пояснения разбиваются до 3500 UTF-16 единиц с сохранением порядка и привязки.

## Запуск, диагностика и поставка

Сервисные настройки читаются из отдельного `.env`: Telegram-токен/группа,
OpenAI-ключ/модель, пути JSON/БД, лимит ответа и контроль свежести котировок.
Shell-интерполяция запрещена; неизвестные и повторные ключи — ошибка.
Старый `PRICE_TICK` допускается для совместимости, но расчёты используют JSON.
Секреты не входят в стратегию, тестовые фикстуры и обычный release-архив.

| Команда | Назначение |
|---|---|
| `run <env-file>` | Запуск координатора и внешних адаптеров |
| `check-service <env-file>` | Проверка настроек и стратегии без сети |
| `prepare-mt5 <csv> <root> <symbol> <source>` | Подготовка индексных минут из выгрузки баров MT5 |
| `import-history <db> <root>` | Проверенный импорт подготовленных минут |
| `inspect-db <db> <as-of-UTC>` | Просмотр сохранённых минут и закрытых свечей |
| `smoke-test <db> <strategy>` | Автономный искусственный сценарий на новой тестовой БД |
| `probe <env-file>` | Отдельная read-only проверка Telegram getMe/getChat и снимка котировок |

Живые проверки запускаются отдельно по задаче. Smoke-test не использует рабочую БД.

Служебные сообщения и логи заданы в требованиях. Лог H4 не создаётся для повторного,
незакрытого или неполного бара и при загрузке предыдущих свечей. Смена недельного
состояния уведомляет по `weekly_rules`; повтор события не дублирует уведомление.

## Комплект обновления

Deploy исключён из Git; содержит бинарник, рабочий JSON, инструкцию и SHA256SUMS.
Секреты, базы и unit не включаются. Переход на индекс требует нового пустого
пути data/signals.sqlite; старые файлы сохраняются отдельно. Сервис в рамках
разработки не запускается и готовые серверные бинарники автоматически не заменяются.

## Общая библиотека и локальный бэктест

Локальная команда поддерживает --no-pdf и --report-only RESULT_DIR. Результаты
записываются в новый каталог: strategy.json, results.json (включая данные графиков),
events.jsonl, trades.csv, report.pdf. PDF после сбоя можно собрать без повторного
расчёта. Шаги данных не используют рабочую SQLite. Docker монтирует только выбранные
пользовательские каталоги котировок и стратегию read-only; результат writable, сеть отключена.
Python и системные зависимости отчёта закреплены версиями; Python/Rust-образы — digest.

### Визуальное оформление PDF

Утверждённый образец — локальный отчёт `reports/backtests/october-2026/report.pdf`
после обновления оформления 10.11.2026: шесть страниц, включая четыре примера.
Производный PDF не требуется хранить в репозитории; воспроизводимый шаблон —
[backtest/report/render.py](../../backtest/report/render.py). Этот раздел фиксирует
его визуальный стандарт для последующих изменений. Оформление не пересчитывает
сделки, статистику или выбор примеров.

**Страница и типографика.** A4, книжная ориентация, белый фон. Боковые поля
48 pt, верхнее 62 pt, нижнее 49 pt. Шрифт DejaVu Sans с кириллицей встроен в PDF;
для заголовков и значений используется Bold. Главный заголовок — 29/35 pt
(кегль/интерлиньяж), заголовки разделов — 15/20, основной текст — 8,5/12,
примечания — 7/10, таблицы — 7,5/10. Сохраняются свободные поля и ясная иерархия,
без отдельной декоративной обложки.

**Палитра.** Цвета одинаковы в вёрстке и графиках:

**Общие элементы.** Верхняя тёмно-синяя полоса высотой 43 pt содержит белые
`FOREX / RESEARCH` слева и `BACKTEST / версия` справа. Внизу — тонкая линия,
пометка локального расчёта, первые 12 символов хеша правил и номер страницы
двумя цифрами. Карточки стоят по три в ряд, расстояние 9 pt, высота фона 64 pt,
радиус углов 7 pt. Внутри: небольшая подпись 7,5 pt, короткий цветной штрих
и крупное значение Bold 23 pt. Таблицы имеют тёмно-синюю шапку с белыми жирными
подписями, тонкую бирюзовую линию под ней и чередующиеся белые/светлые строки;
без тяжёлой сетки. Шапка повторяется при переносе. Пустые таблицы не рисуются.
Предупреждения выделяются светлой персиковой плашкой с левой полосой 3 pt.

**Композиция отчёта.**

1. Сводка «Стратегия в цифрах»: период UTC и пары; два ряда карточек
   (результат закрытых, просадка закрытых, число сделок; доля прибыльных,
   средняя сделка, profit factor); кривая R и просадка; краткая оговорка
   методики; таблица результатов по парам.
2. С новой страницы — «Детали и качество данных»: месяцы, длительность,
   открытые/ожидающие/отменённые сигналы, покрытие котировок, плашка пропусков,
   объём начальных свечей, происхождение и хеш правил, методика исполнения.
3. Каждый пример начинается с новой страницы: номер разбора, крупные пара
   и направление, три карточки (реализованный R, вход, исходный стоп), время
   и правило, предупреждение при наличии пропусков. Затем два крупных графика
   друг под другом: POI на D или W и вход на H4. Внизу — пояснение о снимке
   основания и последующих свечах.

Количество страниц адаптируется к объёму таблиц и примеров; шесть страниц
образца не являются лимитом. При изменении шаблона проверяются извлечённый
русский текст и все отрендеренные страницы: читаемость, переносы, отсутствие
обрезанных подписей и наложений. Проверки пустого отчёта и повторяемости PDF
сохраняются; красивое оформление не должно скрывать отрицательные результаты
или ограничения данных.

### Ошибка определения пары сигнала

`signal_text` читает символ из префикса ID (`SYMBOL:...`) и проверяет его
существующим валидатором инструментов. При отсутствующем или некорректном
префиксе возвращается ошибка «Не удалось определить пару сигнала». Вызывающий
Runtime передаёт ошибку выше до записи события и исходящего сообщения.
Подстановка EURUSD удалена; формат текущих корректных ID и снимков не меняется.

## Контракт стратегии v2 (согласовано)

Рабочий JSON и example.json переводятся непосредственно на schema_version=2.
Конвертера, старого загрузчика и чтения чисел из текста нет. Корневые разделы:
comment, schema_version, instrument_price_tick_scale, instruments, candles,
context, parameters, policies, messages. Фактические торговые значения сохраняются.
parameters содержит только действующие настройки в объектах value/comment.
policies явно задаёт реализованные алгоритмы и ограничения; неподдерживаемые
значения отклоняются. Опциональный строковый comment разрешён у объектов,
но не участвует в расчётах. Сообщения хранятся отдельно от условий.

Пять ранее текстовых настроек становятся положительными целыми параметрами:
stop_fallback_h4_bars=10, confirmation_inversion_h4_bars=30,
weekly_fractal_sweep_lookback_bars=60, target_fractal_lookback_d_bars=80,
target_fractal_lookback_w_bars=60. Это значения текущего файла, не константы движка.
weak_bars удаляется: модуль слабости отключён. Отметка снятого дневного фрактала
за 30 баров не реализована и не превращается в действующую настройку.

OpenAI получает документ с пояснениями и каталог разрешённых путей. Может менять
действующие скалярные параметры и comment, но не структуры, инструменты или
фиксированные политики. Неподдерживаемая просьба требует уточнения. Полный кандидат
проверяется перед атомарной записью; незатронутые пояснения сохраняются.
Хеш документа включает comment/messages и используется для восстановления записи.
Расчётный хеш исключает comment/messages: их изменение не пересчитывает планы.
Сохраняются FIFO, защита опубликованных уровней и идемпотентность после сбоя.

Внутри поддерживаемой схемы SQLite снимок с прежним форматом хешей без
незавершённой операции обновляет формат хешей и один раз пересчитывает ожидающие
планы. Идентификаторы, сроки, опубликованные уровни, история, очередь и привязки
сохраняются. Незавершённая операция старого формата останавливает загрузку
с диагностикой без изменения снимка. Это не миграция прежней БД в SQLite v4:
для перехода на индекс используется чистая база.

## Правила «свинг»

`core/src/swing.rs` — расчёт правил «свинг» из требований: свечи, фракталы, зоны, планы,
сделки. Модуль не читает файлы и не знает о бирже; получает закрытые свечи и минутные
максимум/минимум, цены — числа с плавающей точкой, время — секунды сетки источника.
Параметры — структура `SwingConfig` (внутренний `Default` задаёт значения для
конструирования в коде; JSON-конфигурация должна содержать обязательные поля).
Параметры боковика находятся во вложенном объекте `range`. Команда
`forex-backtest swing-replay` читает
выгрузку M1 из MetaTrader 5, строит свечи по сетке сервера и печатает список сделок;
она нужна для сверки с эталонным списком сделок черновика и к подбору параметров не
относится.
`forex-backtest swing-history` прогоняет правила по подготовленным минутам `data/history/<SYMBOL>`
через тот же агрегатор свечей, что и бот (`swing::grid_time` переводит время закрытия
в сетку источника); результат — то, что увидел бы бот на этих данных. Агрегатор отдаёт
правилам «свинг» все закрытые свечи с признаком полноты (`push_all`, `minute_all`);
`push` и `minute` для основного движка по-прежнему отдают только полные. `forex-backtest dxy-build` собирает минутную серию синтетического индекса доллара из шести
выгрузок M1 (формула — `swing::dollar_index`) в том же формате выгрузки MT5; `swing-replay`
с файлом индекса прогоняет по нему отдельный экземпляр правил и передаёт его события
в выход по индексу. В живой работе бота котировки шести пар для индекса пока не подключены.

В боте: `Market.swing` (снимок) хранит `Swing` инструмента, его параметры и уже
опубликованные состояния сделок. `processing::process` отдаёт и все закрытые свечи
(`Batch.all_bars`); `Runtime::tick_logged` передаёт их правилам через `swing::rules_bars`,
затем котировку через `Swing::minute`, и публикует изменения сделок. `Runtime::swing`
подключает правила к инструменту; прогрев по минутам базы — `service::swing_warmup`.
Путь к файлу правил — необязательная настройка `SWING_STRATEGY`. При её отсутствии
или исключении инструмента из файла новые swing-планы и заявки не создаются;
опубликованные Pending/Active сопровождаются в режиме управления по сохранённым
параметрам и уровням, а сигналы основного движка снова публикуются. Неопубликованные
ожидающие планы при отключении не порождают заявок. Старые снимки v4 без признака
режима управления читаются совместимо.
`Swing::compact` после каждой свечи удаляет данные, которые больше не влияют на решения.

Исследовательское расширение: `SwingConfig` выбирает типизированное семейство
на уровне инструмента. Отсутствующее поле семейства в старом JSON и в старом
снимке означает `legacy_swing`; новая конфигурация `trend_pullback` обязана
содержать все параметры семейства и проходит тот же отказ на неизвестные поля.
Счёт EMA и генерация намерения используют только закрытые H4 бары. Генератор
намерений отделён от общего lifecycle сделки: `Trade`, sizing, минутное
исполнение, выходы и snapshot-продолжение остаются общими. Семейство не
подменяет уже опубликованные уровни.

Смешанный JSON может выбирать семейство независимо для каждой пары. Верхний
`comments` описывает объединение leaf-параметров, фактически используемых
инструментами; схема и `validate` проверяются отдельно для каждого семейства.
Общая проверка `cost` требует конечное неотрицательное значение и не меняет
расчёт legacy-уровней. Только `trend_pullback` дополнительно отбрасывает
сделку, если рассчитанный вход, стоп, направленный риск или цель не конечны,
если любая цена входа/стопа/цели не положительна либо риск не положителен.
Это защищает новое семейство от переполнения и непригодных ценовых уровней.

Round 2 добавляет необязательный `max_open_positions` в параметры
`trend_pullback`. При отсутствии поля старый JSON/snapshot продолжает прежнее
неограниченное поведение; если ключ указан, его значение должно быть
положительным целым (`null` не означает отсутствие ключа и отклоняется). Новая
исследовательская конфигурация явно ставит его в `1`. Ограничение
не меняет legacy и риск допускаемой сделки (1R).

Лимит действует только на новые `trend_pullback` входы и общий для инструмента:
Runtime считает Pending/Active позиции текущего и retired `SwingMarket` до
допуска нового сигнала. Core replay использует тот же счётчик по своим
позициям. Уже сохранённые заявки и сделки никогда не отменяются/закрываются
принудительно при смене лимита; если слотов занято больше нового лимита,
входы остаются заблокированы до освобождения. Pending → Active сохраняет один
слот; отмена или терминальный выход освобождает его в принятом порядке событий.
Сигнал, полученный при полном
лимите, отбрасывается без отложенного входа, при этом EMA/context продолжают
обновляться. Проверка допуска происходит до `minute()` обработки выходов этой
же котировки; одновременный выход не освобождает слот задним числом. Старые
экземпляры продолжают сопровождение по исходной конфигурации и уровням.
Runtime-регрессия формирует H4 закрытия через настоящие `Runtime::tick`:
сигнал создаёт TP-сделку без внешней занятости, но блокируется при retired
Pending и Active; блокировка сохраняется после restart, а новый вход допускается
только после освобождения retired позиции.

При смене конфигурации runtime сохраняет старый `SwingMarket` как retired
экземпляр, отключает в нём создание новых планов и продолжает подавать ему
котировки до закрытия его опубликованных Pending/Active сделок. Новый экземпляр
прогревается под новую конфигурацию. Оба экземпляра сериализуются в snapshot;
ключи опубликованных событий включают семью и исходное время сигнала, поэтому
прогрев или рестарт не переиздают прежние сообщения. Старые snapshots без
retired-списка читаются с пустым списком. Это поведение сначала фиксируется
тестами restart/reconfigure и проверкой отсутствия дублей.

Идентификатор сигнала нельзя считать новым только потому, что его позиция
перешла в terminal state и ключ сопровождения был удалён. При повторном
прогреве runtime сопоставляет стабильный signal ID с подтверждёнными сообщениями
снимка и с сообщениями, которые ещё находятся в outbox. Чтение outbox не
подтверждает и не удаляет сообщение. Поэтому delivered и pending terminal
events одинаково предотвращают повторную публикацию и восстановление сделки
для сопровождения; прежний снимок без `retired`-списка остаётся читаемым.
Регрессионный pending-only тест оставляет outbox-события открытия и терминального
выхода недоставленными при пустом `known`, затем сравнивает очередь до и после
restart/reconfigure и проверяет отсутствие повторной публикации/сопровождения.

Торговая сетка времени (UTC-котировка, преобразованная в naive
America/New_York wall-time + 7h) передаётся только в расчёт swing. Текст
события получает исходный UTC timestamp текущего Tick и форматирует его как
RFC3339, включая стандартное смещение `+00:00`. Тот же UTC timestamp
используется для сообщений от текущего и retired экземпляров.

Для исторического сравнения семейство получает ту же M1 историю и агрегатор;
сделки legacy baseline и candidate объединяются хронологически для общей
portfolio MTM-оценки. Это эквивалентно одному interleaved runner только пока
вход одной пары не зависит от позиции или сигнала другой пары. Если будет
добавлен общий лимит риска/допуска, требуется единый портфельный симулятор.
Любое изменение общего исполнения повторно запускает baseline тем же путём.

Источник параметров — qmc-018 JSON с SHA-256
`6ea9e172228b2ebc4d2b6d4948bd77dbcdfdf06539d4b66febf374005ab292f1`.

#### Проект общего admission budget — V4-D4

Проверяется фиксированный round007 profile: EURUSD qmc-027, GBPUSD qmc-086,
USDJPY `rr_fixed=2` / `take_profit=target`; новые параметры не вводятся, риск
каждой допущенной сделки — 1R. Candidate получает optional
`portfolio_admission.max_open_positions=3`; отсутствующий объект оставляет
baseline unbounded. Существующий per-pair TP cap сохраняет область действия.
Main-engine сигналы, не ставшие сделками кандидата, не занимают portfolio slots.

Один сериализуемый admission coordinator используется live Runtime и joint
replay. Каждый `Swing` производит typed `EntryIntent`; принятый intent идёт через
имеющийся lifecycle/executor. Внешний signal ID и compatibility CSV поля
`signal_t`/`fill_t` остаются прежними. Ledger отдельно хранит
`source_quote_time_utc`, `observed_at_utc`, `admitted_at_utc`, `executed_at_utc`,
`exited_at_utc`, а также source row interval, quote/batch IDs, decision,
reservations и initial risk. Для legacy `signal_t=bar.end` и compatibility
`fill_t=bar.end` никогда не переносят causality назад.

Live batch получает `observed_at_utc_ms` от инжектируемых system UTC wall clock
часов сразу после полного ответа `markets()`. Это Unix milliseconds UTC, один
captured timestamp для всех quotes ответа; durable inbox сохраняет его и batch ID
до обработки, повтор использует прежнее значение. В историческом joint replay
полная M1 строка `[start_utc_ms,end_utc_ms)` становится доступна на исключительной
правой границе `end_utc_ms`; все admission/fill/exit, вызванные этой строкой,
имеют это причинное время. Сохраняются исходный интервал и legacy timestamps.
Исполнение цен/событий остаётся как в V3: market entry по предусмотренной
движком цене с неблагоприятным cost, stop перед target по полному M1 high/low,
ранее установленные fill levels. Не добавляется market fill по open или
отдельное исполнение stop/target по open. OHLC не раскрывает точный момент
внутриминутного касания; ledger фиксирует время доступности строки, не
реконструирует касание. Полная строка с доступностью ровно на cutoff исключена
из `[start, cutoff)`; future exits цензурируются, открытые сделки отмечаются
последней строкой, доступной строго до cutoff. Raw CSV compatibility — отдельная
проверка от новых причинных метрик; обе стороны сравниваются одним accounting,
а baseline при необходимости пересчитывается, прежние числа не переносятся.

Два watermarks независимы: `source_watermark_utc` — максимум обработанных
допустимых source timestamps и используется только для source-late;
`observed_watermark_utc` — причинный timestamp последнего обработанного события,
его UTC-minute buckets управляют terminal reserve release. Source time не
сравнивается с observed watermark. Оба сохраняются, retry пользуется сохранённым
batch receive time. Source-late классифицируется по source watermark, сохранённому
до batch; порядок соседних инструментов в batch не меняет классификацию. После
обработки source watermark обновляется максимумом допустимых source timestamps.

Live один полный `markets()` response является одним FIFO `MarketBatch`, одной
atomic transaction и одной observed-minute группой, даже когда source timestamps
пересекают границу минут. Внутри response порядок фаз: occupancy, admission всех
intents по `(observed_at_utc, ASCII symbol bytes, intent_key)`, затем execution и
exits. Выход не освобождает слот для другого входа этого же ответа. Для replay
полная M1 строка относится к правой границе; группы доступности обрабатываются
хронологически и в каждой повторяются occupancy→admission→execution/exit, после
чего продвигается observed watermark. Пример A closes 10:00, B at 10:00 blocked,
C at 10:01 admitted относится к разным replay availability times, не одному live
response. Эквивалентность требует одних и тех же сохранённых causal times/order;
разбиение live ответов, меняющее receive time, не обязано давать тот же выбор.
Весь batch фиксирует coordinator, all Swing checkpoints, outbox и ledger
атомарно; failure не потребляет slot и не оставляет частичного состояния.

Tie-break для доступных intents: `(observed_at_utc, symbol ASCII bytes,
intent_key)`. Внутренний `intent_key` versioned tuple
`(config_generation:u64, family_code:u8, plan_id:UTF-8 bytes,
source_event_ms:i64, direction_code:u8, intent_ordinal:u64)`. Числа сравниваются
численно, строки — bytewise lexicographic; enum codes фиксированы versioned
таблицей. `intent_ordinal` монотонен внутри config generation/symbol/family/plan,
различает correction intents с одинаковыми внешним ID и source event и
сохраняется в snapshot. Hash-map iteration не участвует. Quote dedup key включает
pair/source/source timestamp/price; batch ID защищает от повторной обработки.
Внешний опубликованный signal ID не меняется.

Slot reservations и NS-05 risk — разные шкалы. Pending, Active и terminal
reserves занимают slots; Pending→Active сохраняет один slot. Cancel/Stop/Target
занимает его до `max(terminal_observed_minute, observed_watermark_minute)`
включительно; release возможен только со следующей observed UTC-minute. NS-05
peak open initial risk суммирует только исполненный initial risk Active-сделок
между `executed_at_utc` и `exited_at_utc`, консервативно entry перед exit при
равном времени. Pending не несёт open risk, перевод в Active учитывает initial
risk один раз; terminal reserve не является риском. Peak reserved slots отдельно
диагностирует cap и не заменяет NS-05 gate.

Source-late quote определяется строго как
`source_timestamp < source_watermark_utc`, относительно source watermark до batch.
При включённом `portfolio_admission` она не создаёт новый admission. Без общего
cap статус только диагностический и не блокирует прежний locally valid entry;
per-symbol TP cap, local dedup и source ordering сохраняются. В обоих режимах
локально допустимая late quote сопровождает existing Pending/Active, включая
retired. Вызванные ею fill/exit датируются captured `observed_at_utc_ms` и не
пересчитывают прошлое; освобождение slot не раньше следующей observed-minute.
Это исправляет область запрета D3: запрещён только новый capped admission.

`source_watermark_utc` восстанавливается из сохранённых source timestamps.
Если старый snapshot не имеет `observed_watermark_utc`, запрещено выдавать
`Tick.millis` за время получения. При первом обрабатываемом batch его captured
observed time единожды сохраняется как `bootstrap_observed_at_utc_ms`; старый inbox
без такого поля получает фактическое время начала первой обработки. Retry
использует уже сохранённый timestamp. Occupancy восстанавливается из всех
current/retired Pending+Active без изменения trade условий. При включённом cap
admission закрыт на всю первую observed-minute bootstrap, но управление
существующими Pending/Active работает сразу; admission возобновляется строго со
следующей observed-minute при наличии слота. Bootstrap time/barrier сохраняются
через restart. Без общего cap этот барьер не блокирует local admission. После
batch source watermark становится максимумом допустимых source timestamps;
observed watermark остаётся отдельными causal часами и управляет только
minute-based terminal reserve. Source timestamps никогда не сравниваются с
observed watermark.

Config switch задаёт `switch_at_utc_ms` — UTC millisecond успешного атомарного
commit проверенной конфигурации, вместе с новым `config_generation`. Source-grid
`bar.end` переводится в UTC тем же DST-aware преобразованием. Для новой
конфигурации `bar.end_utc <= switch_at_utc` — только контекст, даже если бар
впервые обнаружен после gap. Новый intent допускается только от
`bar.end_utc > switch_at_utc` и при фактическом наблюдении после границы;
равенство относится к старой конфигурации. Retired pending/active продолжают
сопровождаться на старых уровнях, а их причинные exits влияют на общий slot.
Switch time, generation, current/retired Swing, coordinator watermarks, outbox и
ledger сохраняются одним commit. Cold start совместно прогревает потоки всех
пар одним coordinator; pair warmup с постфактум фильтрацией запрещён. Старый
snapshot восстанавливает slots из current/retired Pending/Active без изменения
условий. Source watermark берётся из saved source timestamps; отсутствующий
observed watermark инициализируется только captured observed time первого batch
(или началом первой обработки старого inbox без поля), не `Tick.millis`. При cap
admission barrier занимает первую bootstrap observed-minute, но существующие
сделки/ордера сопровождаются и исполняются сразу; barrier и captured time
сохраняются так, чтобы restart не сбрасывал и не устанавливал его заново. Без
cap barrier не блокирует local admission.

При полном cap legacy plan остаётся `WaitEntry`, его сроки/уровни прежние;
обработанный trigger помечается, скрытой очереди нет, повторный вход только от
нового самостоятельного события. Context/индикаторы продолжают обновляться.
Range rejection не создаёт Trade/`Sweep`, не увеличивает stop counter и не
проверяет противоположную сторону на том же H4 событии.

До реализации Docker RED покрывает: M1 open выше target при low, коснувшемся
stop, сохраняет Stop V3 stop-first по full high/low; строка, доступная ровно на
cutoff, исключена; V3 market price/cost/fill levels и raw CSV parity проверяются
отдельно от пересчитанного baseline. Один live response с source timestamps по
разные стороны минуты образует одну observed-minute admission-before-execution
группу без same-response release. Проверяются предbatch source watermark,
обычная delivery latency без ложного source-late, locally valid source-late quote,
которая сопровождает current/retired Active и исполняет stop на captured observed
time без нового capped admission, а rebound не отменяет выход. Сценарий выполняется
capped/uncapped и после restart; release не раньше следующей observed-minute.
Replay availability 10:00/10:01 проверяет A-close/B-block/C-admit. Отдельные RED:
Pending reservation без open risk и один Active risk после fill; correction
tie-break после restart; config switch после gap и late H4; старый snapshot без
source/observed watermark, restart без сброса bootstrap barrier; один и тот же
locally valid source-late H4 intent разрешён uncapped и запрещён capped при
одинаковом management существующих сделок. Дизайн ждёт review; код/backtests не
разрешены.

## Адаптер котировок Upscale

bot/src/upscale.rs читает котировки через GET /accounts/with-risk-status и
/v2/markets?accountId=... с Bearer-ключом. API base фиксирован в CLI,
заменяем в тестах. Settings хранит ключ отдельно от стратегии.

| Символ стратегии | ticker | baseAsset | quoteAsset |
|---|---|---|---|
| EURUSD | EUR/USD | EUR | USD |
| GBPUSD | GBP/USD | GBP | USD |
| USDJPY | USDJPY/USD | USDJPY | USD |

Таблица описывает внешний протокол, список инструментов берётся из JSON.
market_id читается из API, проверяется формат UUID. Дубли и несовпадения
идентичности отклоняются, обратная котировка не предполагается.

IndexQuote хранит source=upscale, исходный положительный index_price_fp9
(i64, масштаб 1e9), blockTimestamp UTC ms, идентичность и closed/paused/close_only.
Будущее время, некорректные поля и устаревшие открытые рынки отклоняются.
Давность ограничивает QUOTE_STALE_SECONDS; для closed/paused или планового
перерыва старый снимок допускается только как статус, а не тик.
Close-only не мешает сигналам.

IndexQuote также хранит `schedule` из этого же ответа: `inPause`, `pausedAt`,
`nextPauseAt`, `nextUnpauseAt` и совместимые поля `closestPauseAt`,
`closestUnpauseAt`. `null` означает круглосуточный рынок; отсутствующее поле
или некорректный объект отклоняется. Время — целые неотрицательные Unix ms,
значения `0` и `9007199254740991` сохраняются без преобразования в дату.
При `inPause=true` worker передаёт только MarketState, без Tick и без
ошибки потока из-за давности цены. Плановый перерыв учитывается вместе с
прежними closed/paused при допуске котировки; его начало и конец не создают
уведомлений в чат. После `inPause=false` действуют прежние проверки свежести.
Опрос всех рынков продолжается одним GET; локальные таймеры по границам
расписания не заменяют следующий ответ API.

HTTP: timeout 30s, connect timeout 10s, redirect запрещены, ответ ≤2 MiB.
Ошибки содержат HTTP-код, машинный код Upscale (если получен) и числовой
Retry-After, без ключа, текста message и полного тела ответа.
Worker run запрашивает все рынки один раз и разбирает пары независимо.
Период — 2s после ответа; 429 — Retry-After, минимум 2s, по умолчанию 60s;
другие ошибки — 5s. Повторы/обратное время обрабатывает существующий Runtime.
Живой сервис использует только адаптер Upscale. Общий feed содержит Tick и
Aggregator; протокольные парсеры прежнего поставщика и его сетевые зависимости
не входят в приложение.

probe-upscale <env-file> читает снимки всех активных демо-счетов без записи
в БД и без Telegram/OpenAI. probe также проверяет Telegram getMe/getChat.
Демон для проверки API не запускается. Торговые методы адаптера не вызываются
из run, probe или probe-upscale.
Предыдущий scripts/upscale_markets.py остаётся диагностическим прототипом.

Контракт: [счета](https://docs.upscale.trade/ru/developers/operations/getaccountswithriskstatus),
[рынки](https://docs.upscale.trade/ru/developers/operations/getmarkets).

Торговые методы того же Client:

- `open_market` принимает счёт, рынок, long/short, резерв amount и leverage;
  отправляет POST /orders с type=market.
- `active_positions` выполняет GET /positions/{accountId}/active и возвращает
  idx, market, direction и size каждой позиции.
- `close_market` принимает счёт, рынок, positionId, направление позиции и
  объём amount; отправляет POST /orders с type=take и triggerPrice="0".
  Полный size закрывает всю позицию, меньший amount — её часть.

Оба POST принимают x-idempotency-key от вызывающего кода и возвращают id,
status и errorCode ордера. Все шесть статусов ордера из API сохраняют свой
смысл; canceled_by_error возвращается с причиной, а не как подтверждение
исполнения. Запросы проверяют UUID и положительную целочисленную запись fp9;
числа передаются строками без округления или ограничения диапазоном float.
Используются прежние HTTP-клиент, Bearer, таймауты, запрет redirect и лимит
ответа. Нет автоматического повтора POST, расчёта суммы/плеча или скрытых
дополнительных запросов. Методы не меняют SQLite и не отправляют уведомления.

Контракт торговли: [создание ордера](https://docs.upscale.trade/ru/developers/operations/createorder),
[открытые позиции](https://docs.upscale.trade/ru/developers/operations/getactivepositions).

## Единая индексная цена

Единственная цена свечей, входа, стопа, цели и отмены — индекс Upscale.
Котировка содержит symbol, millis (UTC, миллисекунды), price (целое в масштабе
1 000 000) и source. Цена положительна. Старый двухценовой формат не поддерживается.
Политики выбора стороны цены удаляются из JSON; candles.price_basis=index.
Рыночный вход и стоп используют наблюдаемую цену; лимит и тейк — заданный уровень.
Комиссии, своп и дополнительные издержки не моделируются.

База создаётся с нуля по DATABASE_PATH=data/signals.sqlite. Старые файлы БД и
архивы не изменяются и не подключаются; преобразование старых данных не выполняется.
Бот восстанавливает только своё новое состояние; автоматического прогрева из архива нет.
Индексный бэктест использует общий обработчик котировок и требует достаточной
истории индекса. Отсутствующие интервалы не заполняются, происхождение сохраняется.
Формат истории описан в [history-data.md](../history-data.md).
Загрузка истории Upscale не реализуется в этой задаче.

Новая SQLite-схема v4 создаётся непосредственно, без цепочки миграций.
Предыдущие версии не изменяются и не открываются как индексное состояние.

Подготовленные индексные минуты должны непрерывно покрывать публикуемую свечу.
Пропуск между минутами или gap_before_minutes прерывает полноту открытых свечей;
недостающий конец интервала не заменяется последней ценой. Для подготовленных
минут источник сведений о пропуске — поле gap_before_minutes (и gaps набора);
проверка по времени предыдущей котировки применяется к живым тикам.
Закрытие рынка с пятницы 16:00 до воскресенья 17:00 America/New_York пропуском не
считается: последняя пятничная свеча закрывается полной, первая свеча новой недели
(W и D) продолжает полноту от неё, даже если первая котировка пришла позже 17:00.

Адаптер переводит исходный fp9 в масштаб 1e6 целочисленным округлением к ближайшему,
половины вверх. Результат записывается в Tick.price; нулевая цена отклоняется.
Проверка source=upscale:index находится в живом runtime; общий обработчик
используется также бэктестом с явно указанным источником индексной истории.
